开发一个 Windows 优先的 Avalonia 桌面 coding agent 客户端，通过 Pi 官方 RPC 驱动 Pi。AI 负责实现、构建、测试、诊断、修复、打包和维护开发记录。用户负责提出需求、评价使用体验，以及完成必须本人进行的登录或授权，不承担 C# 代码审查工作。

已经确定：

- 桌面使用 C# / Avalonia，不再重新选择 WinUI 3。
- 使用官方 Pi 进程与 RPC，不移植 Pi 内核，不自行实现模型供应商协议或 Agent 循环。
- 产品支持插件，第一版采用 Pi 扩展机制；没有兼容特定既有 Pi 插件的要求。
- Windows 本机项目和工具链优先；WSL、远程执行、跨平台发布留待后续需求。
- 先交付可实际使用的单会话应用，再实现多会话、插件管理和发布体验。
- 开发以真实交付和必要验证为准，避免为了防错遍历全部代码或反复执行无关回归。

首版用户路径：

> 启动应用 → 选择项目 → 配置一个可用模型 → 提交任务 → 查看流式消息与工具执行 → 在需要时批准或停止 → 查看结果 → 关闭应用 → 重开并继续原会话。

第一版不包含：完整 IDE、通用 C# 插件 SDK、插件市场、自研终端模拟器、多 Agent 编排、后台系统服务、远程 RPC 服务器、自研 Windows 沙箱。这些不影响首版支持 Pi 工具和 Pi 扩展。

## 4. 责任分配与架构

```text
Avalonia Views / ViewModels
            |
Desktop session coordinator + local metadata
            |
C# Pi RPC client + child-process host
            |
      stdin/stdout JSONL
            |
Official Pi process
  |-- providers / model streaming
  |-- agent loop / tools / compaction
  |-- sessions / branches / persistence
  `-- Pi extensions
        `-- Fufucode approval and UI bridge extension
```

| 能力 | 责任方 |
|---|---|
| 模型请求、重试、压缩、工具循环 | Pi |
| 对话与分支持久化 | Pi |
| 模型选择与思考等级执行 | Pi；桌面提供选择界面 |
| 运行状态、消息时间线、工具卡片 | 桌面 |
| Pi 子进程启动、停止、诊断 | C# 进程宿主 |
| 项目列表、会话索引、草稿、窗口偏好 | 桌面本地存储 |
| 工具执行前的应用审批 | Pi 扩展负责等待与阻止；桌面收集决定 |
| 第三方扩展的工具和命令 | Pi 扩展 |
| Windows 文件打开、目录定位 | 桌面平台服务 |

官方 RPC 是本地管道通信，不需要另起 HTTP/WebSocket 服务。RPC 不等于远程服务，也不自动提供外部 C# 工具回调能力；需要增加工具时先写 Pi 扩展。

```text
  Fufucode.Pi/                   # RPC DTO、JSONL、进程、版本能力

  fufucode-bridge/               # 少量 TypeScript 扩展代码

  Fufucode.FakePi/               # 可控的假子进程，用于真实管道测试
  fixtures/                     # 人工合成或脱敏的协议记录
scripts/                        # 构建、检查、真实 RPC 验证与打包
docs/
  AI_DEVELOPMENT_PLAN.md
  progress.md
  decisions.md
  runtime-baseline.md
  verification.md
```

这些是职责边界，不要求第一天就创建所有目录或空接口。Windows 小型辅助实现可先留在相应项目中；只有被多个调用方使用或需要替换时再抽象。

## 5. AI 的执行方式

每次实施遵循以下循环：

1. 阅读本计划、当前进度和相关源文件，确认上一次真正完成到哪里。
2. 选择一个可独立验证的小任务，说明本次完成标准。
3. 编写代码并构建；测试应验证外部行为或具体风险，而不是复制实现逻辑。
4. 运行本任务所需测试；影响核心链路时补一条端到端验证。
5. 失败就定位修复，不通过跳过断言、掩盖错误或放宽终态条件制造成功。
6. 记录改动、结果、未验证项、下一步；交付可运行程序或明确的中间成果。
7. 已授权且未受阻的工作继续进行，不把常规技术选择反复交给用户确认。

用户无需审核 C#。需要用户参与的内容限定为账号登录、必要的凭据提供、产品偏好与真实使用反馈。缺少真实模型凭据时，AI 可以继续完成模拟协议与界面工作，但必须保留真实模型验收为未完成。

不会自动开展多 Agent 开发。只有用户明确要求或适用约定要求时再委派；届时每个子任务仍需有明确文件范围与验收依据。

开发记录必须简洁：

- `progress.md`：里程碑状态、当前任务、阻塞项、下一步。
- `decisions.md`：影响长期实现的选择及原因，不记录每个小改动。
- `runtime-baseline.md`：真实运行环境和协议支持表。
- `verification.md`：运行过的验证、结果、证据位置、尚未验证的限制。

若实施时仍没有 Git，可初始化本地仓库并设置忽略项以建立检查点；不创建远程仓库、不推送、不改写用户已有历史。不得因计划提到 Git 就在本次编写文档时开始实施。

## 6. RPC 客户端实施规格

### 6.1 进程启动与退出

- 通过明确的可执行文件路径和参数列表启动；避免拼接一条复杂 shell 命令。
- Windows 使用重定向 stdin/stdout/stderr 的隐藏子进程，不弹出控制台窗口。
- 优先直接启动应用管理的 Node 与 Pi CLI 入口，避免依赖 `.cmd` 包装和 shell 引号行为。具体入口从所选包中核实，不猜路径。
- 每个 Pi 进程的工作目录绑定一个项目；切换项目时创建对应进程，不伪装成只修改 C# 字段。
- 启动后立即持续读取 stdout 与 stderr，再发送状态命令。
- 启动成功以有效 RPC 响应为依据，不以“进程没有立即退出”为依据。
- 正常关闭通过关闭 stdin 请求 Pi 退出；等待有界时间，超时再清理所管理的进程树。
- 应用关闭、进程异常退出时，所有等待中的请求必须结束并获得可解释错误。
- 常规取消使用 RPC，不直接杀进程；进程无响应时的强制结束是单独动作。
- 首版退出应用就结束所管理的 Pi 工作；托盘后台持续运行是后续功能，不做隐式常驻。

### 6.2 JSONL 传输

- 使用 UTF-8，发送一个完整 JSON 对象加 LF；接收时按 LF 拆帧，允许前面有一个 CR。
- 支持一条记录被拆成多次管道读取，以及一次读取包含多条记录。
- 正确处理跨读取边界的多字节字符；U+2028/U+2029 不得被当作记录边界。
- stdin 使用单一序列化写入路径，避免并发命令写成交错 JSON。
- stdout 的读取不能等待 UI 弹窗、Markdown 渲染或磁盘慢操作。
- 传输读取和协议状态处理分离；UI 更新可以合并，协议状态与最终事件不得静默丢弃。
- 队列和单条记录设置合理资源上限，考虑长历史与图片；超限给出明确错误，不能截断成看似合法的数据。
- stderr 只作诊断，不混入消息或当成 JSON 协议解析。
- JSON 数据通过结构化序列化写入，不用字符串插值手工拼 JSON。
- `JsonDocument` 的生命周期明确；保留 `JsonElement` 时复制或转换，避免释放后引用失效。

### 6.3 请求、事件与超时

- 每条请求生成唯一字符串 ID；按 ID 匹配响应，支持响应乱序。
- 连接代次标记用于区分进程重启前后的请求和事件。
- 命令响应、会话事件、扩展 UI 请求分开路由。
- 缺少 ID 的 parse 错误作为协议异常处理，不随机归给某个请求。
- 短查询设置请求期限；模型运行时长与查询超时分别处理。
- 客户端超时不证明命令没有执行。超时的 `prompt`、shell 等有副作用操作不自动重发。
- 新增未知字段默认兼容；未知非关键事件保留有限诊断。关键协议缺失或不兼容要明确报错，不能猜测成功。
- UI 错误信息区分命令拒绝、模型失败、用户取消、进程退出和协议错误。

### 6.4 运行生命周期

- 先安装事件接收与状态处理，再发送 `prompt`，避免快速响应时漏事件。
- `prompt` 成功响应只说明接收或处理结果。处理 `started`、`queued`、`handled`。
- `handled` 不保证启动 Agent 运行，不得固定等待 `agent_settled`。
- `agent_end` 是低层运行结束，不表示重试、压缩和排队任务已经全部结束。
- 当前参考协议用 `agent_settled` 表示自动工作已结束；实际版本须在 M0 验证。
- `agent_settled` 只表示不再自动继续，最终成功、失败或中断须结合消息与错误事件判定。
- Pi 的 `turn` 表示一次 assistant 响应与其工具结果；桌面用户看到的一轮任务可能包含多个 Pi turn，模型名称须区分。
- 会话事件通常没有命令 ID，不把每个事件强行关联到最近发送的请求。

### 6.5 停止、插入与队列

- 默认“停止”按钮先 `clear_queue`，再 `abort`；明确处理返回的队列内容，保存为待恢复文本，不覆盖已有草稿。
- 仅 `abort` 可能让队列中剩余内容继续执行，因此不能把两者当作等价。
- 停止过程中阻止新的提交竞态；已有请求与队列事件按顺序收敛。
- 运行中发送新消息时，让用户选择插入指令或排队；通过官方 `steer` / `follow_up` 或对应 `streamingBehavior` 实现。
- 队列接收成功不意味着已经执行；显示实际队列状态。
- 若后续加入直接 RPC `bash` 操作，单独处理其 `abort_bash`，不假定普通停止覆盖所有入口。

### 6.6 消息重建

- 使用 `message_start` 建立临时消息，按 `contentIndex` 维护文本、思考和工具调用块。
- `text_delta` / `thinking_delta` 追加到对应块；不要把不同块混成一个字符串。
- `toolcall_delta` 可能只是未完成 JSON，展示为临时文本，不当成可执行参数。
- 用块结束内容替换相应临时块；`message_end.message` 是整条消息的最终依据，避免重复追加。
- 工具卡片按 `toolCallId` 对应。`partialResult` 是否追加由工具契约决定，不能统一当增量；最终结果覆盖展示状态。
- 顶层流式 usage 是累计值，不能逐条相加。全会话统计优先读取 `get_session_stats`。
- 压缩后的未知用量显示为未知，不把 null 显示成零消耗。
- 只展示 Pi 实际返回的思考内容；没有数据时不伪造占位推理文本。
- 流式刷新合并执行，结束事件立即刷新。Markdown 渲染不能对每个字符反复解析全部历史。

## 7. 会话、状态与数据归属

### 7.1 状态模型

不要把全部情况压成一个 `IsRunning`，也不要设计巨大组合枚举。分别记录：

- 连接：Stopped / Starting / Connected / Faulted / Stopping。
- 活动：Idle / Running / Compacting / Retrying / Cancelling。
- 用户交互：待处理扩展 UI 请求集合；审批等待是可叠加状态。
- 最近任务结果：Completed / Failed / Interrupted / Unknown。

错误和通知不是终态的唯一依据。进程启动失败与模型请求失败采用不同恢复入口。

### 7.2 数据存储

建议应用数据根目录使用当前用户 LocalApplicationData 下的 `Fufucode`：

```text
Fufucode/
  runtime/<version>/              # 应用管理的 Pi 与运行环境
  pi-agent/                      # 应用专属 Pi 配置
  sessions/<project-id>/          # Pi 管理的会话文件
  desktop.db                     # 项目、会话索引、草稿与偏好
  logs/                          # 有上限的脱敏诊断
  exports/                       # 用户主动导出的资料
```

- 用 `PI_CODING_AGENT_DIR` 指向应用专属配置，明确传入 `--session-dir`。
- 不自动复制或修改用户全局 Pi 配置。若需要导入，提供明确的一次性导入流程。
- RPC 冒烟测试可以用 `--no-session`；需要恢复的产品会话必须启用持久化。
- 桌面数据库只保存会话路径、项目、排序、草稿等元数据；可保存可重建的展示缓存，不把它变成第二份权威对话历史。
- 正常消息写入、压缩和分支由 Pi 执行，桌面不直接重写 Pi 会话文件。
- `get_messages` 用于当前模型对话状态，不足以代表压缩前历史和全部分支。完整历史按版本能力使用 `get_entries` / `get_tree`。
- `get_entries` 的 since 指针是持久化 entry ID，不是实时 RPC 事件的全局序号。
- 不假设存在列举所有会话的 RPC。首版记录本应用创建或明确导入的会话；目录发现若需要，使用选定版本的文件格式并保持只读。
- 重新连接时先重建状态，再接收新工作；首版禁止用户在恢复快照尚未完成时发送任务，避免重复渲染和状态交错。
- 进程中断后，不自动重发最后一次 prompt 或工具调用。用户看到中断状态后可继续提出新要求。

### 7.3 多会话与进程数量

- 首先实现一个活动会话和一个 Pi 进程。
- 多会话阶段采用一个活跃会话对应一个 Pi 进程，防止状态交叉。
- 首版默认只允许一个同时运行的 Agent 任务；其他聊天可显示历史和草稿。后台并行运行作为独立增量增加。
- 同一会话文件不能同时交给多个可写进程；桌面启动与恢复须做所有权检查。
- 空闲回收只有在无运行任务、无待审批、无未完成请求时执行。
- 项目身份用规范化绝对路径和稳定 ID 表示；不要仅靠文件夹名称区分项目。

## 8. 工具审批、项目信任与插件

### 8.1 首版边界

Pi 使用启动它的 Windows 用户权限；工作目录与 RPC 进程隔离都不是文件访问沙箱。

应用内置审批扩展只控制经过相应工具调用路径的操作。第三方扩展本身可以执行代码，不能宣称审批扩展隔离了所有插件。

开发早期真实任务在临时工作区运行。进入日常项目使用前实现审批路径，避免把审批推迟到产品末期。

首版默认策略：

- 明确的文件读取、搜索可按配置自动执行。
- 文件写入和 shell 执行请求一次性确认；后续按实际需求加入更细的允许规则。
- 未知自定义工具默认请求确认。
- 关闭弹窗、超时、连接丢失均按拒绝处理。
- 第三方扩展按可信本地代码加载；应用不声称限制其全部副作用。

这些是产品初始默认值；用户明确配置的偏好可以调整。不要根据命令名称或字符串前缀声称某个任意 shell 命令“只读”。

### 8.2 审批实现

- Pi 桥接扩展在执行前的 `tool_call` 处理路径请求确认，并等待决定。
- 验证所选 Pi 版本的阻止返回值、处理顺序、参数变更和错误行为，不凭旧示例实现。
- 使用 `ctx.ui.confirm` / `select` 等官方接口，通过 `extension_ui_request` 与 `extension_ui_response` 往返。
- 桌面显示工作目录、工具、关键参数和拟执行动作；大的内容可以展开。
- 一次批准对应具体请求与参数；参数被其他处理器改变后，不得继续套用旧批准。无法保证时限制该组合并报告边界。
- 相同请求只响应一次，旧进程或旧会话的审批 ID 不得用于新连接。
- 审批请求不会阻塞 stdout 消费；它只阻塞对应工具的继续执行。
- 不靠观察 `tool_execution_start` 才弹窗，因为此时执行可能已经开始。
- 直接 RPC `bash`、扩展命令内部执行、包安装等可能不经过该工具钩子。首版不开放直接命令入口；以后增加时单独定义控制路径。
- 桥接扩展未加载或握手验证失败时，不把 UI 上的“审批已开启”视为事实，不开放受控写入模式。
- 验证拒绝后文件确实未改变、命令确实未执行，不能只检查收到了一条拒绝消息。

### 8.3 项目信任

- 项目信任决定是否加载项目资源；它不是每次工具操作的审批。
- RPC 模式不能显示 Pi 内置的终端信任提示，桌面必须主动给出决定路径。
- 未明确授权加载项目扩展时使用对应的跳过策略；用户同意后按选定版本规则重启或重新加载。
- 不为省事对所有项目无条件传 `--approve`。
- 官方文档说明 `AGENTS.md` 等上下文文件可能不受项目信任控制；界面和说明不得称拒绝信任就完全不会读取项目指令。
- 应用显式控制会话目录，避免项目会话设置悄悄改变本应用的存储位置。

### 8.4 插件首版范围

实现：

- 加载用户明确选择的本地 Pi 扩展。
- 列出本应用管理的扩展路径、启用状态和最近加载错误。
- 工具、扩展命令、技能、模板通过 Pi 官方机制生效。
- 支持 select、confirm、input、editor，以及 notify、status、文本 widget、标题和输入框文本请求。
- 输入框被插件赋值时保护用户未发送草稿，采用可恢复替换或明确提示。
- 协议请求超时后能关闭失效弹窗；客户端保持待请求清理，不假设服务端超时会自动清理本地 UI。
- 不支持的 TUI 自定义控件标记为不支持；不能承诺任意终端插件界面自动转换为 Avalonia。

首版扩展启停通过安全停止后重启进程生效。插件市场、自动更新与任意依赖安装另行开发；若扩展已有依赖，按其已固定的项目配置准备，并记录安装来源与结果。

## 9. 界面和认证规格

界面采用普通桌面信息层次：项目/会话侧栏、对话时间线、输入区、运行状态与设置。

首版需要：

- 用户消息、assistant 内容、可折叠思考、工具输入输出、错误和运行状态。
- 代码块复制、Markdown 基础排版、长输出折叠；图片在模型支持时通过 RPC 的 images 内容发送。
- 不把 PDF 或任意附件直接当成 images 字段发送；文件引用需单独制定支持范围。
- 中文输入法组合期间 Enter 不误发送；快捷键与停止操作有清楚行为。
- 流式期间用户上翻历史不会被强制拉回底部；提供回到最新位置入口。
- 模型与思考等级从 Pi 查询，不把文档示例中的模型名称或等级写死。
- 工具修改内容展示优先使用结果中的结构化信息或可靠文件差异。Git diff 可能包含用户原有修改，必须区分项目差异与本次操作，不能把全部差异归因于 Agent。
- 首版不提供“一键撤销所有修改”；任何撤销功能须另行设计以保护用户已有改动。

认证分两步：

1. 开发原型使用一个明确配置的环境变量或应用专属 Pi 认证目录；日志不能输出凭据。
2. 发布版提供受支持供应商的设置流程。API key 可由 Windows 保护存储保存，启动时只注入需要的配置；OAuth 优先使用 Pi 官方支持的登录流程和存储，不另写认证协议。

普通 RPC 不能凭空完成未公开的登录操作。`/login` 等 TUI 内置命令不得直接假设可由 `prompt` 执行。若需要交互式认证辅助进程，应提供用户可见入口，并先验证所选版本的完整登录流程。

环境变量可能被工具子进程继承；加密保存只保护静态存储，不表示运行期插件无法接触凭据。不要为实现认证而打印或复制用户全部环境与 auth 文件。

代理、端点等设置仅作用于本应用管理的进程。自定义端点配置沿用 Pi 支持的模型配置结构，先验证最常用的一种，再扩展设置界面。

## 10. 按里程碑执行

### M0：建立基线与可重复启动

任务：

1. 复核本地工程、适用 AGENTS.md 和已有冒烟脚本。
2. 检查 SDK 与依赖可用性，先构建现有欢迎页；保留已有有效工作。
3. 准备应用专属 Pi 运行目录，核实实际发布版本与本文命令匹配。
4. 建立版本记录、日志目录、临时测试工作区和最少的开发记录。
5. 用无模型调用的 RPC 命令验证启动、查询、正常退出。

交付：可重复的构建入口、RPC 基线记录、无凭据的诊断结果。

完成条件：从新的终端或应用进程中可复现有效 RPC 响应；缺少运行环境时有明确诊断；不能只记录进程启动成功。

### M1：可靠传输与进程宿主

任务：

## 12. 性能测量与工程限制

不承诺未测量的性能数字。M2 记录首个基线，M7 用相同机器和数据复测。

分别记录：

- 应用打开到窗口可交互的时间。
- Pi 启动到状态查询成功的时间。
- RPC 接收内容到界面可见的本地延迟，和模型首 token 等待分开。
- 整个应用进程组的空闲、任务中与历史加载后的内存；明确统计口径。
- 合成流量下的 CPU、输入响应与停止响应。
- 关闭应用后的进程残留。

优化根据证据进行。优先控制活动进程数量、历史加载量、重复字符串、流式 UI 更新和 Markdown 重算。Node 子进程的成本真实计入结果，不能只展示 Avalonia 主进程内存。

日志默认不记录完整 prompt、工具文件内容、认证头或 token。记录事件类型、请求 ID、耗时、退出码和脱敏错误即可。详细协议录制作为明确启用的开发选项，限定目录与保留大小，导出前再次脱敏。

## 13. 完成定义、停止条件与交接

一个里程碑只有同时满足以下条件才能标为完成：

- 可从源码构建对应产物。
- 该阶段必要验证已实际运行并通过。
- 产品行为符合验收描述，不靠假数据冒充真实模型或真实 Pi。
- 错误状态可解释，没有已知永久等待或静默丢失任务的路径。
- 进度与验证记录反映事实。

状态只使用：未开始、进行中、待外部条件、已完成。未验证项必须留在记录里，不能因为 AI 认为代码正确就勾选。

遇到以下情况应调整方案并记录：

- 所选发布版没有计划依赖的命令或事件。
- 插件 UI 能力超出官方 RPC 表达范围。
- 认证必须人工完成。
- 当前工具环境无法运行桌面 UI 验证。
- 真实行为与官方文档或 fixture 不一致。

这些情况不要求停止所有开发。AI 应继续无依赖的工作，对确实受阻的验收保留状态，并向用户说明具体缺什么。

阶段交接格式：

```text
本次完成：具体功能及所在文件
验证：实际命令或 UI 操作、结果、证据位置
未完成：明确的功能或未验证项
当前可运行入口：准确路径与启动方式
下一步：一个可执行任务及完成条件
```

不承诺“几小时全部完成”或预先给出没有校准的 token 总预算。先完成 M0～M2，记录实际耗时和可获取的 token 用量，再估算后续；没有用量数据就不编造数字。
