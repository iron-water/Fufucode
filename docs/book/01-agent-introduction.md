# 第一章对照：Agent 的最小构成与 FUMO 的边界划分

## 一个公式，两种读法

李博杰在《深入理解 AI Agent》开篇给出一个工程公式：Agent = LLM + 上下文 + 工具，随后把它展开为 Agent = Model + Harness，其中 Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正。这个公式的价值不在于定义，而在于它划出了一条可操作的边界：哪些代码属于 Agent，哪些属于环境。

FUMO 的代码结构几乎是对这条边界的直接实现。`NativeAgentLoop` 只负责循环；`PureCSharpAgentEngine` 负责历史与压缩；`ProductionToolDispatcher` 负责工具接口与约束；`OpenAiCompatibleModelClient` 负责与模型的往返。四者之间没有交叉引用，边界是编译期确定的，而不是靠约定维持的。

## 循环：状态机而不是递归

大多数 Agent 教程里的循环是一个 `while (true)` 加若干 `if`。FUMO 把它写成显式状态机，并给每一次模型调用编号：

```csharp
using var iterationSpan = PerfTracer.Step("agent.iteration", "n", PerfTracer.Invariant(iterations));
```

`iterations` 不只是计数，它是预算的载体。循环在每轮开始判断是否仍有预算，在接近上限时注入提示，在最后一轮撤走工具。这个设计对应书里提到的预算感知问题：标准 Agent 缺乏预算意识，即使给足步数也会早早饱和。FUMO 的做法不是单纯调大上限，而是让模型看见剩余空间。

一个具体例子：`survey` 类任务在修复前，模型会把全部轮次用于读文件，最后一轮仍调用工具，随后被硬截断，输出 36~146 个 token。修复后同一任务输出 1403~1667 个 token，命中率从 0/5 升到 3/5。差别不在模型，在于循环是否告诉模型"你快没时间了"。

## 上下文：三层结构

FUMO 的上下文不是一条平铺的消息列表，而是三层：

**静态层**——系统提示、工具定义。这一层在每个回合重建，但内容稳定。工具定义按名称排序后发送，目的是让前缀字节级一致，从而命中 KV Cache。实测长任务缓存命中率约 96%~99%。

**动态层**——用户消息、模型回复、工具结果。只追加，不改写。这是缓存友好的前提，也是压缩必须谨慎的原因。

**状态层**——计划快照、预算提示、压缩台账。这一层由代码确定性维护，不依赖模型记忆。书里把这称为"Agent 状态栏"：把算好的结论加进上下文，而不是指望模型自己归纳。

FUMO 的实现里，状态层有三种载体：`update_plan` 维护的结构化计划、`[预算提示]` 注入的轮次信息、`[压缩时保留的状态台账]` 记录的文件与命令。三者的共同点是——它们都在压缩后原样保留，因为摘要模型看不到这些结构。

## 工具：接口即能力边界

书里有一个判断：底层模型固定时，提升 Agent 表现最有效的手段往往是重新定义观察空间与动作空间。FUMO 的八个内置工具就是这条判断的具体化：

| 工具 | 观察还是动作 | 边界设计 |
|---|---|---|
| `read_file` | 观察 | 按行分页，超限给续读 offset |
| `grep_search` | 观察 | 按文件分组、相关度排序、游标分页 |
| `glob_files` | 观察 | 遵守 .gitignore，跳过构建产物 |
| `list_dir` | 观察 | 不递归，只给一层 |
| `write_file` | 动作 | 覆盖语义，JSON 写盘前校验 |
| `edit_file` | 动作 | 唯一匹配，失败报行号 |
| `run_command` | 动作 | 工作区沙箱，进程树超时清理 |
| `update_plan` | 状态 | 单 in_progress 约束 |

这张表的每一行都对应一个曾经出过问题的地方。`edit_file` 的唯一匹配约束来自多次"改错文件"的实际故障；`grep_search` 的分组输出来自平铺结果被大文件淹没的实际问题；`read_file` 的分页来自超长文件被循环层二次截断的实际缺陷。

## 约束、验证、纠正

书里把 Harness 的三层保障拆成约束、验证、纠正。FUMO 的实现：

**约束**——权限模式（Default/AcceptEdits/Plan/Auto/BypassPermissions）、工作区路径沙箱（含符号链接逐级解析）、Plan 模式只声明只读工具。约束的特点是在动作发生前生效，而不是事后检查。

**验证**——写盘前 JSON 解析校验、工具结果的结构化状态、子代理的 `Truncated` 标记、回合终态的显式枚举。验证的特点是它产生可判断的信号，而不是模糊的"看起来没问题"。

**纠正**——`edit_file` 失败时报出匹配行号、`grep_search` 截断时给收窄建议、预算耗尽前注入提示、断流后重试并重放。纠正的特点是它把错误变成下一步的输入，而不是终止。

## 一个反例：什么时候不该加机制

FUMO 早期有一批"想当然"的防御性默认值：HTTP 100 秒超时、400k 字符压缩线、120 秒命令超时、固定 temperature 0.2、`context_lines` 上限 5、人工确认 60 秒超时。它们的共同点是没有真实任务分布依据，只在防御想象里成立。

真实长任务暴露了后果：100 秒超时杀死了长推理请求；400k 字符线让压缩时机与模型真实窗口脱节；固定 temperature 让推理型模型直接拒绝请求。

这条经验对应书里"苦涩的教训"的务实版本：Harness 补的是模型当前做不稳的部分，而不是把所有能想到的风险都编码成默认值。每加一条约束，都应该能回答"它在真实任务里防住了什么"。

## 本章要点

- FUMO 的四层结构（循环、引擎、调度器、客户端）是 Model–Harness 边界的直接实现。
- 循环的轮次计数是预算载体，不是简单计数器。
- 上下文分静态、动态、状态三层；状态层由代码维护，不依赖模型记忆。
- 工具设计的每一处约束都应有真实故障作为依据。
- 防御性默认值需要任务分布支撑，否则会成为新的故障源。
