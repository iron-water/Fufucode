# 第二章对照：FUMO 的上下文工程

## 静态前缀：为什么工具要排序

书里用一整节讲 KV Cache：前缀任何字节变化都会让之后的缓存全部失效。对 Agent 来说，这意味着两件事——工具定义和系统提示必须稳定，历史必须只追加。

FUMO 在工具声明上做了一个具体的选择：

```csharp
foreach (var tool in request.ToolNames
             .Distinct(StringComparer.Ordinal)
             .OrderBy(t => t, StringComparer.Ordinal))
```

按名称字典序发送，而不是按注册顺序。原因是插件加载顺序不确定——同一组插件在不同机器上可能以不同顺序注册，如果不排序，工具声明的前缀就会抖动，缓存全部失效。

这个改动的效果可以测量：长任务实测的缓存命中率在 96%~99.3%。某一轮的典型数据是 `promptTokens=18823`、`cachedTokens=18688`，即 99.3%。

需要澄清一个容易误解的点：FUMO 没有发送任何显式的缓存标记（`cache_control`、`ephemeral`、`prompt_cache_key` 都没有）。它完全依赖服务商的隐式前缀缓存，代码只负责把前缀做稳定，并读回服务商报告的缓存命中数。这对 OpenAI 兼容端点是合理的——多数网关按前缀自动缓存，不需要客户端声明。

系统提示的稳定性则更难保证。FUMO 的 `BuildTurnMessages` 每次回合都会重新拼接：项目约定 + 计划快照 + 技能目录 + MCP 服务器 + 子代理目录 + 插件人格。其中至少三项是变量：

- 计划快照随 `update_plan` 变化；
- 插件人格可能随插件启停变化；
- `AGENTS.md` / `CLAUDE.md` **每个回合都从磁盘重读**，文件一改，前缀立刻失效。

第三点是一个可以优化但尚未优化的地方：项目约定属于低频变化内容，按文件修改时间缓存就能避免无谓的缓存击穿。当前实现选择了简单——每回合重读，正确性优先。

这是一个已知的权衡：动态信息的价值高于缓存损失。计划更新不频繁（一次任务通常 3~10 次），缓存失效的代价是一次性的；而计划一旦丢失，长任务会重复已完成的工作。

## 动态提示：Skills 的渐进披露

书里把 Skills 描述为"渐进式披露"：目录常驻，正文按需加载。

FUMO 的实现：

**发现**——扫描六个位置：项目的 `.fumo/skills`、`.agents/skills`、`.claude/skills`，用户目录的同名三个。每个技能是一个包含 `SKILL.md` 的目录。

**目录注入**——系统提示里只放名称与描述，格式是紧凑列表。技能多的时候这部分会膨胀，但每条只有一行。

**按需加载**——模型调用 `skill` 工具，传入名称，返回完整的 `SKILL.md` 正文加基目录路径加附带文件清单。

**权限分层**——`disable-model-invocation: true` 的技能不进入模型可见目录，只能由用户通过 `/skill:name` 显式调用。这对应书里提到的注入面问题：第三方技能的内容如果藏有恶意指令，效果比网页隐藏文本更直接。

## 状态栏：三种确定性维护

书里提出"Agent 状态栏"的概念：在上下文里注入由代码算好的元信息，弥补模型无法主动归纳隐式状态的缺陷。

FUMO 有三处实现，都在压缩后原样保留：

**计划快照。** `update_plan` 维护的结构化步骤，压缩后作为独立消息保留。理由是摘要模型看不到这个结构——它不在对话文本里，只在调度器的内存里。

**预算提示。** 剩余轮次不足时注入 `[预算提示]`，要求模型先收敛再决定是否继续检索。这个提示只在已发生工具轮之后注入，避免挤占用户原始请求的位置。

**状态台账。** 压缩时生成，记录已改文件、最近 8 条命令与退出码、失败工具次数。这些是确定性事实，不依赖摘要模型。

三者的共同设计原则是：**代码能算出来的，就不要让模型去记**。模型记不住的，压缩后一定会丢；代码算出来的，压缩后可以原样重建。

## 压缩：从字符阈值到真实窗口

FUMO 的压缩策略经历过一次根本性修正。

**旧版本**：固定 400k 字符阈值。问题是这个数字没有依据——不同模型的窗口差十倍，400k 字符对 128k 窗口的模型太晚，对 1M 窗口的模型太早。

**新版本**：按模型真实 `context_length` 判断，85% 触发。窗口未知时才退回物理字符保护（2M 字符）。判断依据优先用上一次真实 usage，恢复的历史没有 usage 时用 `chars/2` 保守估算。

这个改动对应书里的一条原则：压缩时机应该基于真实窗口，而不是拍脑袋的字符数。

## 压缩保真：四层保留

书里提到压缩最大的风险是约束丢失——有研究显示压缩后策略违规率可以从 0% 升到 30~59%。FUMO 的应对是四层保留：

**第一层：系统提示原样保留。** 不参与压缩。

**第二层：所有用户指令逐字保留。** 早期版本只钉住"第一条足够长的用户消息"，后来改成按顺序保留所有用户指令（8k 字符预算）。原因是用户常在后续回合追加硬约束——"不要动 main 分支"、"只用标准库"——这些恰恰最容易被压缩丢掉。

代码不做内容判断，因为判断"哪句重要"需要语义理解。代码只保证不丢。

**第三层：状态台账。** 已改文件、命令与退出码、失败次数，由代码从工具调用记录里提取。

**第四层：最近窗口。** 8 条消息 + 120k 字符双约束。只按条数限制不够——8 条超大工具结果同样会撑爆上下文。

摘要本身用固定的七段结构：用户目标与硬约束、已完成工作、关键决策、错误与修复、验证状态、待办与下一步、关键事实。固定结构的作用是让摘要可预测——模型知道去哪找什么。

实测结果：连续压缩后，原始约束仍能被模型完整复述（3/3 次召回全部三条硬约束）。

## 上下文腐化：一个尚未量化的风险

书里区分了上下文溢出（装不下）与上下文腐化（装得下但找不到）。FUMO 解决了前者，后者还没有量化手段。

理论上，FUMO 的设计对腐化有一定缓解：状态台账把"需要归纳的结论"变成了"可以直接检索的事实"，压缩把冗长的工具输出换成了结构化摘要。但这些都是定性判断，没有测量。

要测量腐化，需要构造这样的实验：同一任务，一组在长上下文下运行，一组在压缩后的短上下文下运行，比较决策质量。FUMO 当前的探针做不到这个——它只能测最终结果，测不了中间决策质量。

这是一个已知的评估缺口。

## 本章要点

- 工具按字典序声明，保证前缀稳定；实测缓存命中 96%~99.3%。
- 系统提示每次重建，计划快照会破坏缓存，但价值高于损失。
- Skills 三层：目录常驻、正文按需、权限分层。
- 状态栏三处实现（计划、预算、台账）都由代码维护，压缩后原样保留。
- 压缩从固定字符阈值改为按模型真实窗口，85% 触发。
- 压缩保真四层：系统提示、用户指令、状态台账、最近窗口。
- 上下文腐化尚未量化，是已知评估缺口。
