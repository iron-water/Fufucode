# 第三章对照：FUMO 的知识供给，一个刻意的空缺

## 先说结论

FUMO 没有用户记忆系统，没有 RAG 管线，没有向量检索，没有知识图谱。`Fufucode.Core` 里搜不到 embedding、向量库、文档切分、召回排序的任何实现。

这不是遗漏，是当前定位下的选择。但"不做"需要说清楚替代方案是什么，否则读者会以为是能力缺失。

## 替代方案一：项目约定文件

FUMO 在每次回合组装系统提示时，读取工作区根目录的 `AGENTS.md` 或 `CLAUDE.md`，注入到系统上下文（**每回合重读，不缓存**）：

```
## 项目约定（自动加载自 AGENTS.md）
<文件内容>
```

只读根目录第一个存在的文件，限长 32k 字符，超出时保留头 24k + 尾 8k，中间折叠。

这个设计解决的是"仓库级事实"——项目用什么构建、有哪些约定、哪些目录不能动。这类知识的特征是：**数量少、变化慢、每次任务都需要**。它不需要检索，因为全量放进上下文也不会撑爆窗口。

书里讨论用户记忆时提到跨会话保存的偏好。FUMO 在这一点上有部分覆盖：`AppSettings` 保存模型选择、思考等级、执行模式等，这些是应用级偏好而非知识。真正的"用户偏好记忆"（比如"这个人喜欢简洁回答"）没有实现。

## 替代方案二：Skill 作为可检索的知识

书里把 Skill 描述为"按需查阅的参考资料"。FUMO 的实现让 Skill 承担了一部分知识库的职责。

一个 `SKILL.md` 可以写任何东西：某个 API 的调用方式、某个框架的约定、某类任务的流程。它放在项目的 `.fumo/skills` 或用户目录下，通过名称与描述被发现，通过 `skill` 工具加载。

这个机制与 RAG 的区别在于**检索方式**：RAG 按语义相似度自动召回，Skill 由模型主动按名称选择。前者适合海量非结构化文档，后者适合少量结构化流程。

FUMO 选择后者，理由是 Coding 任务的知识形态：你不需要"从一万篇文档里找出相关的三段"，你需要"知道有个叫 pdf 的技能，需要时打开看"。前者的检索成本高，后者的目录成本低。

代价是：当技能数量增长到几十上百个时，目录本身会占用可观的上下文，而模型选择技能的准确率会下降。这时才需要 RAG 式的检索。FUMO 还没到这个规模。

## 替代方案三：会话历史本身

FUMO 的会话历史是持久化的 JSON，包含完整的消息、工具调用、用量。重开会话时历史恢复，模型能看到之前做过什么。

这是最朴素的"记忆"：不分层、不检索、不抽象，就是原样保存。它的局限很明显——跨会话不共享（除非恢复同一个会话），不提炼（不把"这次学到的东西"变成知识），会随长度增长而必须压缩。

但它有一个优点：**可审计**。每条消息都能追溯到具体的时间、工具调用、模型响应。RAG 检索出的片段往往丢失上下文，而原始历史不会。

## 为什么不做 RAG：三个理由

**第一，Coding 任务的知识密度分布不同。** 通用 RAG 面对的是海量文档，其中大部分与当前问题无关。Coding 任务的知识就在仓库里——需要什么读什么，`grep_search` 和 `read_file` 就是最好的检索器。为代码库建向量索引，不如让模型直接搜索源码。

**第二，维护成本高于收益。** RAG 管线需要：文档切分策略、embedding 模型、向量库、增量更新、召回排序、重排。每一环都有调参空间，每一环都可能成为故障点。而 FUMO 的定位是零外部依赖的桌面应用——引入 embedding 模型意味着几百 MB 的运行时和一次性的索引构建。

**第三，当前规模不需要。** 一个项目的 `AGENTS.md` 通常几千字，技能通常个位数，源码用 grep 就能定位。RAG 的价值在数据量超过检索能力时才会显现，FUMO 的用户还没到这个量级。

## 两个"存在但没接线"的东西

仓库里其实有两处以记忆或知识为名的实现，但都没有接入 Agent，需要区分清楚，避免误以为 FUMO 已有记忆能力。

**ResidentCore 的分层记忆。** `Fufucode.Fufu`（桌宠模块）里有一个 `ResidentCore`，定义四个作用域：IDENTITY、USER、PROJECT、AGENTS.md，读写 Markdown 文件并记录观察日志。数据结构是完整的，但**没有任何消费者**——`ReadMemory` / `WriteMemory` 只在测试里被调用，`FufuSessionHost` 也没有把它的内容注入任何系统提示。它处于"第 1 阶段"状态，即只有存储层，没有接线。

**资料库（Library）的全文检索。** `workspace.library` 插件有自己的 SQLite 存储、CJK 二元组倒排索引和 token 搜索。但它**没有向 Agent 暴露任何工具**——`CreateToolHandler` 返回 null。也就是说，用户可以在资料库里搜索，模型不能。

这两处说明一件事：FUMO 里已经出现了记忆与知识检索的构件，但产品层面还没有决定让模型使用它们。这不是技术障碍，是接线决策。

这三个理由都可能随规模变化而失效。如果将来一个用户有几百个技能、几十个仓库、需要跨项目知识复用，RAG 就会变成必需品。当前的判断是"还不到时候"，不是"永远不做"。

## 一个真实的失败：知识注入的位置

FUMO 曾经把 `AGENTS.md` 的内容放在用户消息里而不是系统提示里。后果是：每次回合都追加一份，历史迅速膨胀，压缩时又被当成对话内容处理。

修复方式是移到系统提示，且只读一次。这个改动看起来是实现细节，实际影响很大：系统提示在压缩时原样保留，用户消息会被摘要。

这条经验对应书里的一条原则：**静态知识与动态对话应该分层**。混在一起会让压缩策略失效——你不知道该保留哪些、该摘要哪些。

## 知识注入的安全面

书里专门讨论了知识库投毒：检索到的文档如果含有恶意指令，效果与提示注入相同。

FUMO 的 `AGENTS.md` 自动加载有一个明确的风险：如果仓库是别人给的，`AGENTS.md` 里可以写任何指令，而它会被当作系统提示的一部分。这比用户消息里的注入更危险，因为模型对系统提示的信任度更高。

当前没有任何防护。没有来源标记，没有指令过滤，没有"这段内容来自仓库而非用户"的提示。

这是一个已知的未处理风险。缓解手段可以有很多（来源标注、内容审查、权限降级），但都还没做。诚实地说，这是当前设计的一个缺口。

## 本章要点

- FUMO 没有 RAG、向量检索、知识图谱，是定位选择而非遗漏。
- 三个替代方案：项目约定文件（仓库级事实）、Skill（按需查阅的流程知识）、会话历史（可审计的原始记录）。
- 不做 RAG 的三个理由：Coding 知识就在仓库里、维护成本高、当前规模不需要。三个理由都可能随规模失效。
- 知识注入必须放在系统提示层，不能混进用户消息，否则压缩策略会失效。
- `AGENTS.md` 自动加载存在投毒风险，当前无防护，是已知缺口。
