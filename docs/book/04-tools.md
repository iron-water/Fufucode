# 第四章对照：FUMO 的工具生态与披露策略

## 工具分类：三个方向

书里按调用方向把工具分成五类：感知、执行、协作、事件触发、用户沟通。FUMO 的内置工具只覆盖前两类，协作与用户沟通交给插件。

| 类别 | FUMO 实现 | 位置 |
|---|---|---|
| 感知 | `read_file`、`list_dir`、`grep_search`、`glob_files` | 内置 |
| 执行 | `write_file`、`edit_file`、`run_command` | 内置 |
| 状态 | `update_plan` | 内置 |
| 协作 | `subagent` | 可选插件 |
| 感知（外部） | `mcp` 网关 | 内置能力，需配置 |
| 用户沟通 | 审批通道（ExtensionUiRequest） | 会话内 |

这个分布是刻意的：内置工具只做"任何编码任务都需要"的事，其余全部插件化。好处是默认安装包小、攻击面窄；代价是用户需要主动安装才能获得完整能力。

## 工具形态：专用、通用、Skill 三选一

书里给了一个四维决策框架：安全与权限、参数复杂度、变更频率、模型能力。FUMO 在三处做过这个判断，结果各不相同。

**`run_command` 是通用执行器。** 按书里的默认取向，通用工具优于专用工具，除非有明确的安全、权限或性能理由。FUMO 没有为 `npm test`、`dotnet build`、`pytest` 各做一个工具，只给一个 shell。理由充分：这些命令的参数结构简单，模型生成命令行的可靠性与生成 JSON 相当；而专用工具会让工具数量随生态膨胀。

**`edit_file` 是专用工具。** 按书里的例外条款，"参数结构复杂"值得独立工具。`old_string` / `new_string` 的语义（必须逐字一致、必须唯一匹配）无法用 shell 命令可靠表达，用 `sed` 会引入转义地狱。这正是书里说的"参数复杂度"维度。

**Skill 是知识而非工具。** FUMO 的 `SkillRegistry` 只暴露一个 `skill` 工具，模型调用它来加载 `SKILL.md` 的完整内容。这是书里"渐进式披露"的直接实现：系统提示里只有技能目录（名称 + 描述），正文按需加载。

三者的分工很清楚：**能确定性执行且参数简单的 → 通用执行器；参数复杂或需要结构化校验的 → 专用工具；只是流程知识、不需要代码执行的 → Skill。**

## 渐进披露：MCP 的三层收敛

FUMO 的 MCP 支持是一个渐进披露的完整案例。

**第一层：会话启动时不加载任何 MCP 工具。** 系统提示里只有服务器名称与传输方式，没有工具清单。

**第二层：模型主动查询。** 调用 `mcp` 工具的 `list_tools` 动作，才返回某个服务器的工具列表与 schema。schema 超过 4000 字符会截断。

**第三层：按需调用。** `mcp` 工具的 `call` 动作执行具体工具，结果标注 `[MCP server/tool]` 前缀，提示这是外部不可信内容。

这个设计与书里描述的 Claude Code、Codex 的 tool search 思路一致：静态前缀只保留索引，完整 schema 按需注入。区别是 FUMO 用的是一个代理工具（agent tool）而不是 API 层的 `defer_loading` 标记——后者需要模型和服务商双重支持，前者在任何 OpenAI 兼容端点上都能工作。

代价是每次调用多一次往返。收益是：即使接了十个 MCP 服务器、几百个工具，会话启动时的上下文占用仍然接近零。

## 插件工具：能力门禁而不是工具白名单

FUMO 的插件工具注册表有一个设计值得单独说：它按**能力**（capability）门禁，不按工具名。

```csharp
public enum PluginCapability
{
    BrowserControl,      // agent.browser-use
    ComputerControl,     // agent.computer-use
    ReverseLab,          // tool.seep-reverse-lab
    AutoDevelopment,     // automation.auto-dev
    SandboxExecution,    // sandbox.nvx
}
```

插件注册工具时必须声明它属于哪个能力。调度时先查该能力对应的插件是否已安装并启用，未启用则返回具体原因（"插件未安装"而不是"工具未注册"）。

这个设计的价值在错误信息上。用户看到"浏览器控制插件未启用"能立刻知道该做什么；看到"工具 browser_click 未注册"则完全无从下手。

注册表还有一个约束：插件工具不得与内置工具同名。这不是防冲突的技术需要（字典本来就能处理），是防止插件静默覆盖内置行为——一个叫 `read_file` 的插件工具会让所有安全假设失效。

## 工具数量：当前 8 个，上限在哪

书里提到工具超过一百个时，即使最先进的模型也容易选错。FUMO 当前是 8 个内置 + 按需的 skill/mcp/subagent + 插件工具。

实际使用中，插件工具是主要的膨胀源。浏览器插件 13 个工具，电脑操控 4 个，加上 MCP 后端可能几十个——如果一个用户全装了，会话启动时可能面对 50 个以上的工具声明。

FUMO 对此只有部分缓解：

- **Plan 模式裁剪**——只声明只读工具与 `update_plan`，插件工具全部不声明。
- **MCP 走网关**——不直接暴露后端工具。
- **插件按能力门禁**——未启用的插件不贡献工具。

但没有做的是：**插件工具本身的渐进披露**。一个装了浏览器插件的会话，13 个 `browser_*` 工具会全部出现在工具列表里。这是当前的一个已知缺口——书里提到的按需加载、检索式预筛选都还没实现。

## 感知工具的一个具体设计：grep 的输出形状

书里讨论 ACI 时强调工具应对应 Agent 的目标，而不是底层 API 操作。`grep_search` 的演进是这个原则的实例。

最初的实现是平铺输出，每条一行，上限 100 条。问题在真实任务中暴露：前 100 条可能全来自同一个大文件。

改造后的输出按文件分组、按命中密度排序、支持文件级游标分页。这个改动不涉及正则引擎（还是 .NET 的 `Regex`），只改输出形状，但直接影响了模型能否在第一次调用中就找到目标。

同一原则还体现在两处细节：

- **空结果显式说明**。"未找到匹配项"是结论，不是失败。工具描述里明确写了这一点，避免模型反复重试。
- **截断给收窄建议**。达到上限时不是简单说"已截断"，而是给出"加 glob / 缩小 path / 提高 max_matches"三条具体路径。

## 一个未实现的能力：事件触发

书里把事件触发列为独立工具类别。FUMO 在这块是空的，而且有一个容易误解的地方需要澄清。

`automation.cron` 插件名字里有 cron，但它的存储结构只有 `DueAt`，没有 cron 表达式、没有重复规则。实际驱动是一个 1 秒的 UI 定时器，检查到期任务并发送——**只支持一次性任务，且应用必须在运行**。

这不是缺陷报告，是事实澄清：插件名与实际能力不符，容易让用户误以为支持周期调度。真正的后台常驻能力在 `automation.auto-dev` 里，它有独立的 BackgroundHost 进程、SQLite 状态库、worktree 生命周期管理——但那套东西服务于开发任务编排，不是通用定时器。

## 本章要点

- FUMO 内置工具只覆盖感知与执行，协作与用户沟通全部插件化。
- 工具形态三选一：通用执行器（run_command）、专用工具（edit_file）、Skill（知识类能力）。
- MCP 用三层渐进披露：启动只给服务器名，按需查 schema，按需调用。
- 插件按能力门禁而非工具名，错误信息指向可操作的下一步。
- 插件工具的渐进披露尚未实现，是当前已知缺口。
- `automation.cron` 只支持一次性任务，名称与能力不符。
