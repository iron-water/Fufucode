# 第五章对照：FUMO 作为 Coding Agent 的取舍

## 七个核心工具，FUMO 有八个

书里给出一个极简 Coding Agent 的工具箱：代码解释器、Bash、读文件、写文件、编辑文件、Glob、Grep。FUMO 没有代码解释器（纯 C# 内核，不内嵌 Python 沙箱），多了一个 `update_plan`，共八个。

这个差异不是缺失，是定位选择。代码解释器的价值在于把"精确计算"从模型的概率推理里拿出来交给确定性执行。FUMO 把这部分交给了 `run_command`——用户环境有什么语言就用什么，不预装运行时。代价是模型必须自己判断环境里有没有对应工具；收益是零外部依赖，安装包不带 Python 或 Node。

`update_plan` 是书里没列但 FUMO 认为必需的一项。原因来自长任务实测：32 轮以上的任务如果没有结构化计划，模型会重复已完成的工作。计划不是给用户看的进度条，是给模型的锚点——而且它在压缩后必须原样保留，因为摘要模型看不到 `update_plan` 维护的状态。

## 工具粒度：为什么是 edit_file 而不是 apply_patch

书里讨论了专用工具与通用执行器的谱系。在文件编辑这一项上，业界有两种主流做法：

**补丁式**（apply_patch）——模型输出 unified diff，工具负责应用。优点是表达力强，一次可以改多处；缺点是对格式极其敏感，上下文行数错一行就整个失败。

**精确替换式**（str_replace）——模型给出 old_string 和 new_string，工具做唯一匹配替换。优点是容错好，模型只需要复制它刚读到的文本；缺点是一次只能改一处。

FUMO 选择后者，理由是实测：在 32 轮长任务里，模型对"复制刚读到的三行"的准确率显著高于"生成格式正确的 diff"。这与 SWE-agent 的 ACI 研究结论一致——精确复现被编辑行的编辑方式，比让模型构造补丁更可靠。

为了让这个选择不变成负担，FUMO 补了三件事：

1. **多匹配时报行号**。模型看到"在第 45、112 行均有匹配"，就能补上下文重试，而不是盲目重试。
2. **成功后回显局部 diff**。模型当轮就能确认改对了，不必再读一次文件。
3. **写盘前校验 JSON**。对 `.json` 目标，替换后的内容必须能解析，否则拒绝写盘并给出行号。这对应书里提到的 linter 思路——在错误进入磁盘前拦住它。

第三条只对 JSON 生效，不做 `.cs` 的伪校验。C# 没有廉价的单文件解析器，硬做只会引入误报。这是一个明确的取舍：能可靠验证的才验证，不能的如实不做。

## 搜索：从平铺到分组

书里提到 Pi 刻意不内置 MCP，优先建议把能力封装成带 README 的 CLI，再由 Skills 按需加载。这个思路的延伸是：搜索工具的输出形状，比搜索速度更影响 token 消耗。

FUMO 最初的 `grep_search` 是平铺输出，每条一行 `文件:行号: 内容`，上限 100 条。真实任务里暴露的问题很直接：如果前 100 条全来自同一个大文件，真正需要的另一个文件永远排不到。

改造后的输出按文件分组：

```
## src/Core/Engine.cs (4 处命中)
42: public void Run()
88: public void RunAsync()
...
## src/Core/Loop.cs (1 处命中)
17: Run();
```

排序依据是命中密度——命中越多的文件越可能是定义处。分页用文件级游标，`offset: 2` 表示跳过前两个已看过的文件。

这个改动的依据来自对 `@ff-labs/pi-fff` 的分析：它替换 grep 的收益不在正则引擎（和 ripgrep 是同一个），而在按文件分组、相关度排序、游标分页。FUMO 是纯 C# 内核，不能引入 Rust 二进制，但输出形状可以照搬。

顺带修了一个 O(n²)：原来每次判断是否达到上限都遍历整个结果列表，改成独立计数器。

## 项目理解：从目录到事实

书里描述 Coding Agent 的工作起点是"项目文档化"——先建立对仓库的认知框架，再动手改代码。FUMO 把这个过程交给模型自己完成，但给了两个支撑：

**AGENTS.md 感知**——系统提示里注入工作区规范文件的内容。这不是 FUMO 独创，Claude Code 和 Codex 都有类似机制，但它解决了一个具体问题：模型不需要每轮重新发现项目约定。

**事实优先的结论要求**——子代理的系统提示里明确要求区分"已确认（有文件:行号或命令输出证据）"与"推测"。这条要求来自实测：不加约束时，模型会把"我猜这个函数在这里"和"我读到了这个函数"混在一起说。

## Harness 工程：三层保障在 FUMO 的落点

书里把 Harness 拆成约束、验证、纠正。在 Coding Agent 语境下，FUMO 的具体实现是：

**约束**——工作区沙箱不只是路径前缀检查，还逐级解析符号链接。原因是：工作区内若存在 `link -> C:\outside`，`link\victim.txt` 会通过前缀检查但实际指向外部。这个细节来自一次真实的越界测试。

**验证**——工具结果带结构化状态（成功/失败/截断），而不是只有文本。子代理的 `Truncated` 标记让父会话知道"结论可能不完整"，避免把半成品当定论。

**纠正**——`read_file` 超限时给续读 offset，`grep_search` 截断时给收窄建议，`run_command` 超时时保留已捕获的输出。纠正的核心是让失败携带下一步信息。

## 一个尚未解决的取舍

FUMO 的工具输出预算是字符数（48KiB 读、64KiB 循环层），不是 token 数。字符与 token 的比例在不同语言、不同内容下差异很大：中文大约 1:1，英文大约 4:1，代码介于两者之间。

这意味着同一份预算在不同任务下的实际占用可能差三倍。改成 token 预算需要本地分词器，而 FUMO 的零依赖定位不允许引入。当前的折中是：字符预算设得足够宽松，让循环层的 64KiB 成为真正的约束点，并在工具层就按行边界截断，避免二次切割。

这不是最优解，是一个已知边界的可用解。

## 本章要点

- FUMO 用 `run_command` 替代代码解释器，换取零外部依赖；代价是模型需自行判断环境能力。
- `edit_file` 选精确替换而非补丁，依据是长任务实测中模型复现文本的准确率更高。
- 搜索工具的价值在输出形状（分组、排序、分页），不在正则引擎速度。
- 写盘前校验只对能可靠验证的格式生效，不做伪校验。
- 字符预算与 token 预算的差异是当前已知的未解取舍。
