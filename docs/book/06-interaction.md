# 第六章对照：FUMO 的观察与动作空间

## 桌面应用本身就是交互接口

书里这一章讨论模态扩展：语音、视觉、GUI 自动化、机器人。FUMO 是桌面应用，它的交互空间不在 Agent 内部，而在宿主外壳上。

这个区分很重要。Agent 内核（`Fufucode.Core`）只处理文本与工具调用；观察与动作的扩展全部在插件层实现，通过统一的工具注册表接入。好处是内核保持纯粹，代价是不同模态的能力差异很大。

## 观察空间：四类输入

| 模态 | 实现 | 状态 |
|---|---|---|
| 文本 | 内置 | 完整 |
| 图片 | `PureImageAttachment`，OpenAI 兼容格式 | 完整，需模型支持 |
| 屏幕 | `agent.computer-use` 的 `computer_screenshot` | 插件，三后端 |
| 浏览器 DOM | `agent.browser-use` 的 `browser_get_dom` / `browser_get_state` | 插件，13 个工具 |

图片输入走的是标准的 `image_url` base64 内联格式。能力探测是异步的：会话先按"支持图片"建立，`ModelCapabilityProbe` 在后台查询模型能力后回写。这样做的原因很实际——本地网关未就绪时，同步探测会让会话打开白等两秒。

屏幕观察有三种后端，按优先级选择：Sky（宿主注入）、CUA Driver、Win32 前台。第三种只在前两种不可用时使用，因为前台模式会抢占用户焦点。截图默认写到 `<project>/output/screenshots`，不直接进上下文——模型拿到的是路径，需要时再读。

浏览器观察走 CDP。13 个工具覆盖导航、点击、输入、滚动、悬停、按键、下拉、等待、取 DOM、截图、取状态。另有可选的外部浏览器桥接（`external_browser_state` / `external_browser_action`），用于控制用户已经开着的浏览器而不是新建实例。

## 动作空间：从文本到 GUI

动作侧的扩展比观察侧更保守，这是有意的。

**文本与文件**是主路径：八个内置工具，覆盖读写、搜索、命令、计划。

**GUI 操作**全部在插件里，且默认不安装。`agent.computer-use` 有四个工具：截图、鼠标、键盘、能力查询。`agent.browser-use` 有十三个。这两个插件的共同点是：它们能做的事情无法用文件工具表达，但也因此风险更高——点击一个按钮可能触发不可逆操作。

FUMO 的处理方式是把它们放在能力门禁之后：未安装不声明，未启用不执行，执行前走审批通道。

**语音**目前只有输出侧。`service.speech-synthesis` 用 Windows SAPI 做 TTS，通过 PowerShell 子进程驱动，支持播放/暂停/恢复/停止。没有语音输入——代码库里没有任何 STT 实现。

这个不对称是当前的真实状态，不是设计选择。语音输入需要麦克风权限、实时流式识别、打断处理，这三样都还没有。

## 异步与事件驱动：一个名不副实的插件

书里把"异步与事件驱动"列为模态扩展的一节，核心是"当世界主动找上门"——定时任务、外部事件触发、长时运行。

FUMO 在这块的现状需要如实说明：

`automation.cron` 插件的存储结构是 `ScheduledTaskItem { Id, SessionId, DueAt, Prompt, AutoRun, State, Error }`。没有 cron 表达式，没有重复规则，没有间隔字段。实际驱动是主窗口里一个 1 秒的 `DispatcherTimer`，检查到期任务，用 Mutex 声明所有权后发送给当前会话。

这意味着三件事：

1. **只支持一次性任务**，不支持周期调度。
2. **应用必须运行**，关闭即停止。
3. **只对当前会话生效**，不能后台派发到其他会话。

真正具备后台能力的是 `automation.auto-dev`：独立的 `BackgroundHost` 进程、回环 TCP 监听、SQLite 状态库、worktree 生命周期管理、100ms 空闲轮询。但它服务的是开发任务编排（WorkPackage 派发、租约、交付卡），不是通用定时器。

这两个插件的命名与实际能力存在落差，用户在插件市场看到 "Cron" 会预期周期调度。这是一个应该修正的表述问题，不是功能缺陷。

## 长时任务：真正的挑战不在模态

书里讨论长时任务时关注的是观察与动作空间的持续扩展。FUMO 的实际经验是：长时任务的难点不在模态，在状态维持。

一次 15 分钟的长任务会经历：30 次以上模型调用、70 次以上工具调用、上下文接近窗口上限触发压缩、可能遇到网关断流。这四件事里，模态扩展一件都不涉及，但任何一件处理不好都会让任务失败。

FUMO 在这块的实现：

**断流恢复**——429/5xx/传输层错误重试；已输出增量时先关闭半成品再重放；SSE 连续失败降级为一次性请求。工具在响应完成后才执行，所以重放没有副作用。

**回合内压缩**——每轮请求前按模型真实 `context_length` 判断，85% 触发。不是固定字符阈值，因为不同模型的窗口差十倍。

**长回合节流落盘**——每 5 秒写一次历史，不是回合结束才写。这样中途崩溃不会丢掉整轮。

**用量可信**——流式请求带 `include_usage`，旧网关不支持时自动降级。用量是压缩判断的输入，不可信就没法做预算。

这四件事都不是"模态扩展"，但它们决定了长任务能不能跑完。

## 一个反例：100 秒超时

FUMO 曾经有一个隐藏的 `HttpClient` 默认超时：100 秒。这个值没人配置过，是 .NET 的默认值。

后果很直接：长推理请求在 100 秒时被终止，表现为"模型无响应"。长任务实测中，两次失败在 2.6~2.9 分钟——正好是重试三次各撞一次超时。

修复方式是移除内部客户端的默认超时，只保留显式配置的 `RequestTimeout`；注入的 `HttpClient` 的超时则归类为可重试的传输失败。

这条经验对应书里"苦涩的教训"的务实版本：Harness 里的每个默认值都应该是深思熟虑的选择，而不是框架的默认。100 秒对聊天够用，对 Agent 长任务远远不够。

## 本章要点

- FUMO 的交互扩展在插件层，内核只处理文本与工具调用。
- 观察侧四类：文本、图片、屏幕、DOM；动作侧以文件工具为主，GUI 操作全部插件化且默认不装。
- 语音只有输出没有输入，是当前真实状态。
- `automation.cron` 只支持一次性任务且需应用运行，名称与能力不符。
- 长时任务的真正难点是状态维持（断流、压缩、落盘、用量），不是模态扩展。
- 隐藏的框架默认值（100 秒 HTTP 超时）是长任务的典型杀手。
