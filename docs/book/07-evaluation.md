# 第七章对照：FUMO 的评估基础设施

## 评估对象是组合体，不是模型

书里有一个关键判断：评估的对象不应只是模型，而是模型与 Harness 的组合体。同一个模型在不同 Harness 里表现可能差一倍。

FUMO 的实测数据支持这一点。同一 survey 任务、同一模型 `auto/glm-5.3-flash`：

| 版本 | 完成情况 | 命中 | 输出 token |
|---|---|---|---|
| 修复前 | 3/3 轮次耗尽 | 0/5 | 36~146 |
| 修复后 | 3/3 正常收敛 | 3/5 | 1403~1667 |

模型权重一个字节都没变。变的只是循环在剩余两轮时是否注入预算提示、最后一轮是否撤走工具。如果不把评估对象定为"模型 + Harness"，这个改进根本无法被观测到——你会以为是模型不稳定。

## 三层可观测性

FUMO 的观测设施分三层，粒度由粗到细。

**第一层：回合级 span。** 每个回合一个根 span `turn`，记录模型、执行模式、提示字符数、是否带图、后端标识、排队耗时。这一层回答"这次交互整体花了多久、走了哪条路径"。

**第二层：阶段 span。** 挂在回合下的固定节点：

```
turn
├── context.build       组装消息与工具定义
├── context.compact     上下文压缩
│   └── model.summarize 摘要模型调用
├── engine.turn         引擎回合
│   └── agent.iteration 每一轮循环
│       ├── model.request
│       │   ├── model.http
│       │   └── model.stream
│       └── tool
│           ├── tool.approval
│           ├── tool.process
│           └── tool.error
├── tool.batch          并行工具批次
└── persist.history     历史落盘
```

这一层回答"时间花在哪"。一次长任务的实测分布是：模型请求占 99.3%，工具执行占 0.7%。这个比例直接决定了优化方向——微调文件读写没有意义，减少模型往返才有。

**第三层：数据落盘。** span 写入 `perf/perf-*.jsonl`，每条记录带 trace id、父子关系、起止时间、标签。这一层回答"能不能离线分析"。

三层之间是解耦的：`PerfTracer` 在未挂载 sink 时零分配，性能监控是可选插件。这意味着评估设施本身不成为生产负担。

## 探针：三类真实端点实验

单元测试验证契约，探针验证行为。FUMO 有三个探针入口，都明确不进默认测试套件：

**`--live-agent-loop`**——最小闭环。读文件、写文件、编辑文件，验证模型请求 → 工具调度 → 结果回填 → 再次请求的完整链路。它回答"这个端点能不能跑通"。

**`--live-session`**——会话层事件。验证流式增量、工具状态事件、停止清理的真实序列。它回答"UI 看到的事件对不对"。

**`--long-horizon-only`**——长程任务定向套件。验证多轮工具循环、压缩触发、断流恢复、落盘节流这些只在长任务中暴露的行为。

前两个探针在当前工作树中仍然存在。**曾经的 `--live-bench` 与 `--live-subagent-bench` 已被删除**——它们是为子代理档位对照而写的，档位归档后依赖的 API 不复存在，探针一并移除。历史数据保留在 `docs/records/fumo-writetex-merge-2026-10-23.md`。

这套探针设计有几个值得保留的选择，即便实现已删：

- **重复 N 次取中位数与范围**，不取单次结果。单次方差极大：同一任务工具调用数可能从 5 到 19。
- **运输失败重试一次**，避免把网关 ECONNRESET 误判成模型或 Harness 差异。
- **命中判定用正则匹配预期事实**，不用 LLM 裁判。成本低、可复现、无主观性。
- **同时记录成功与失败**，失败的任务不剔除，因为失败模式本身就是信息。

## 指标：从 Pass@k 到 Pass^k

书里区分了两种指标：Pass@k 看能力上限（k 次里有一次成功即可），Pass^k 看业务可靠性（k 次必须全部成功）。

FUMO 当前的探针记录的是分布，不是单一分数。这是有意的：`ok=3/3` 和 `ok=3/3 但 truncated=3/3` 是完全不同的结论。前者是成功，后者是"形式上完成、实质上空输出"。

这个区分来自一次真实的误判。早期版本的 survey 任务显示 `ok=True`，但输出只有 36 个 token，命中 0/5。如果只看 `ok` 字段，会得出"子代理可用"的错误结论。加上 `truncated` 和 `hits` 两个维度后，问题才暴露出来。

指标设计的原则是：**每个"成功"都要能被质疑**。一个回合返回 `Completed` 不代表任务完成；一个子代理返回 `Success` 不代表结论正确。所以 FUMO 在结果里同时保留 `Success`、`Truncated`、`Hits`、`ToolCalls`、`DurationMs`，让判断者能看到全貌。

## 失败归因：三类问题，三种修法

书里强调要区分"模型能力不足"和"Harness 设计缺陷"。FUMO 的实际调试过程积累了一个三分法：

**传输层失败**——网关断流、证书错误、SSE error 帧。特征是错误信息里带 ECONNRESET、502、certificate。修法是重试、断流恢复、降级为一次性请求。这类失败与模型和 Harness 逻辑都无关。

**Harness 缺陷**——轮次耗尽但无输出、压缩后丢失约束、工具结果被二次截断。特征是行为可复现、换模型不改善。修法是改循环、改压缩、改工具输出边界。

**模型能力边界**——同一任务下不同模型需要明显不同的工具调用次数。特征是同 Harness 下表现系统性差异。这类不修，只能选择。

三类的区分方法是模型替换实验加重复实验：换模型不改善 → Harness；换模型改善但仍有失败 → 模型边界；随机失败且错误信息指向网络 → 传输层。

## 评估集的现状与缺口

诚实地说，FUMO 当前的评估集是最小版本，缺三样书里强调的东西：

**难度分层**。现在只有 facts（定位三个事实）和 survey（审查五个子系统）两类任务，没有简单/中等/困难的分级，无法判断系统在能力边界上的表现。

**数据泄漏防范**。任务直接问代码库里的常量值，如果模型训练过这个仓库，结果会虚高。当前靠"仓库是私有的"这个假设，不是靠设计。

**统计显著性**。3 次重复能看出方向，但算不出置信区间。书里提到配对比较与排名方法，FUMO 还没实现。

这三样不是不知道怎么做，是当前阶段投入产出比不高。评估设施的价值随任务集规模增长，而 FUMO 的任务集还很小。先把"能重复、能对照、能归因"这三件基础做好，比先建大而全的评测集更实际。

## 本章要点

- 评估对象是模型与 Harness 的组合体；同一模型换 Harness 可以有数量级差异。
- 可观测性分三层：回合 span、阶段 span、JSONL 落盘；未启用时零开销。
- 探针不进默认测试套件，专做真实端点对照实验。
- 每个"成功"都要能被质疑：同时记录 Success、Truncated、Hits 等维度。
- 失败分三类：传输层、Harness 缺陷、模型边界；用模型替换实验区分。
- 当前评估集缺难度分层、泄漏防范、统计显著性，是已知缺口而非疏漏。
