# 第八章对照：FUMO 为什么不做后训练

## 一个空缺，而不是一个疏漏

书里用整整一章讲模型后训练：预训练、mid-training、SFT、RL、蒸馏、奖励设计。FUMO 在这条线上是空的——没有训练管线，没有数据合成，没有奖励模型，也没有微调入口。

这个空缺需要说清楚：它不是"还没做"，而是"当前定位下不该做"。

FUMO 是一个 Agent Harness，不是一个模型。它的代码库是 C#，运行时是桌面应用，分发形态是安装包。训练需要 GPU 集群、数据管线、评测闭环和模型发布流程——这四样都不在 Harness 的职责范围内。把训练塞进 Harness，结果是两边都做不好。

书里其实给了这个判断的依据。它在讨论持续进化时把更新分成四种载体：知识库、Prompt 与 Skill、程序与 Harness、模型参数。前三者属于 Harness，第四者属于训练。一个 Harness 项目能做好前三样，就已经覆盖了大部分可工程化的改进空间。

## 但后训练的思路仍然影响设计

不做训练，不代表不借鉴训练视角。书里对 SFT 和 RL 的讨论，反过来解释了 FUMO 的几处设计选择。

**工具调用的内化程度决定提示词强度。** 书里提到，工具调用曾经靠外部编排，如今已是模型的原生能力。这解释了一个现象：FUMO 的工具描述写得相当详细（每个工具都说明"何时用、何时不用、返回什么"），但对"怎么调用"几乎不做约束。因为现代模型已经内化了 JSON 工具调用的格式，Harness 不需要再教一遍；需要教的是"什么时候该用哪个工具"——这是判断，不是格式。

**奖励设计与验证信号同构。** RL 里的奖励函数要把任务目标变成可计算的信号。FUMO 的验证层做的是同一件事，只是不用于训练：写盘前 JSON 校验、工具结果的成败标记、子代理的 `Truncated` 标记、回合终态的显式枚举。这些信号当前用于运行时纠正，如果将来要做轨迹学习，它们就是现成的标注。

**样本效率解释了为什么不能靠堆轨迹。** 书里讲蒸馏时提到样本效率问题。FUMO 的实测也印证了类似现象：同一任务跑三次，工具调用数可能从 5 次到 19 次，命中率从 2/3 到 3/3。单条轨迹的方差很大，用它做学习信号需要大量对照样本。这也是 FUMO 当前只做"记录轨迹"、不做"从轨迹自动改提示词"的原因。

## 模型替换实验：Harness 的归因工具

书里提到一个方法：固定 Harness，只换模型，观察分数变化。如果换强模型分数不涨，瓶颈在 Harness；如果分数随模型能力大幅波动，瓶颈在模型。

FUMO 的实际测试用过这个方法，结论有参考价值：

同一 survey 任务，`auto/glm-5.3-flash` 下子代理修复前命中 0/5、输出 36~146 token；修复后命中 3/5、输出 1403~1667 token。模型没变，只改了循环的预算提示与最后一轮工具策略。

这是一个清晰的归因：那次失败不是模型能力不足，是 Harness 设计缺陷。如果没有做模型替换对照，很容易误判成"这个模型不行"。

反过来，`devin/swe-2` 在长任务 B 上修复前只有 1/3 完成，两次在 2.6~2.9 分钟被网关断流判死。这类失败归因于传输层，不是模型也不是 Harness 逻辑——修的是重试与断流恢复。

## 如果将来要做，缺什么

诚实地说，FUMO 当前离"可以做后训练"还差三样：

**结构化的轨迹数据。** 现在有 `PerfTracer` 的 span 记录和 JSONL 落盘，但它们是性能视角（耗时、token），不是学习视角（决策点、备选动作、结果好坏）。要做 SFT 数据合成，需要记录"模型在某个状态下有哪些可选工具调用，实际选了哪个，结果如何"。

**可复现的评测集。** 现在有 `--live-agent-loop`、`--live-session`、`--long-horizon-only` 三类探针，但任务集是手写的几个场景，没有难度分层、没有数据泄漏防范、没有统计显著性计算。书里第七章对这些有完整方法论，FUMO 只实现了最小版本。

**失败归因的自动化。** 书里提到"从整条轨迹定位首个错误"。FUMO 现在靠人看日志，没有自动定位首个错误步骤的能力。这是从"有轨迹"到"能用轨迹"的关键一步。

## 本章要点

- FUMO 不做后训练是定位选择：Harness 负责上下文、工具、约束，不负责模型参数。
- 后训练的思路仍然影响设计：工具描述侧重"何时用"而非"怎么调"，验证信号与奖励信号同构。
- 模型替换实验是区分"模型不足"与"Harness 缺陷"的关键方法，FUMO 的实际测试验证过它的价值。
- 要做后训练，当前缺结构化轨迹、可复现评测集、自动失败归因三样基础设施。
