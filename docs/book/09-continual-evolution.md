# 第九章对照：FUMO 没有自动进化，但它留下了证据

## 一个诚实的开头

FUMO 没有任何形式的自动持续进化。没有从轨迹学习，没有自动改提示词，没有自动生成技能，没有自我改进循环。代码里搜不到这类逻辑。

这不是疏忽。书里把持续进化拆成四种载体：经验知识库、Prompt 与 Skill、程序与 Harness、模型参数。FUMO 的四种载体都只能由**人**来更新——开发者改代码、用户改 `AGENTS.md`、用户写 `SKILL.md`。系统本身不会根据运行结果自动改这些。

为什么不做？书里其实给了判断标准：持续进化的起点是可靠的评估。如果系统不知道任务是否完成、哪一步造成了成败，那么自动生成的"反思"只能是猜测。

FUMO 当前的评估能力还停留在"事后人工看数据"的阶段，不具备自动判定"这次运行学到了什么"的基础。在这种情况下做自动进化，产出的会是噪声。

## 但它积累了三类证据

不做自动进化，不等于什么都不记。FUMO 在运行时留下三类可用证据，只是目前靠人来读。

**第一类：性能 span。** 每个回合、每次模型请求、每次工具调用、每次压缩都有独立的 span，带耗时、token、状态、错误。写到 `perf/*.jsonl`，可以离线分析。

这类证据回答"哪里慢、哪里失败"。长任务实测得出的结论——模型请求占 99.3% 时间、工具只占 0.7%——就是从这里来的。这个结论直接改变了优化方向：不再微调文件读写，转向减少模型往返。

**第二类：完整会话历史。** 每条消息、每次工具调用、参数与结果、用量，都存在会话 JSON 里。这是最原始也最完整的轨迹。

它的价值在复盘：一次任务失败后，可以逐条看清模型在哪一步做了错误判断、工具返回了什么、模型如何反应。书里说"原始轨迹不适合作为正式知识单元，但它适合审计"——FUMO 的历史正处在这个位置。

**第三类：对照实验数据。** 探针在重复运行后输出命中率、工具调用数、token、耗时、是否截断。这类数据回答"改动有没有用"，而不是"这次运行怎么样"。早期用于档位对照的 `--live-bench` 已随档位归档一并删除，但当时留下的数据仍记录在 `docs/records/fumo-writetex-merge-2026-10-23.md`。

三类证据的粒度不同：span 是性能视角，历史是行为视角，对照实验是效果视角。做进化需要的是三者结合——知道慢了（span）、知道为什么慢（历史）、知道改了有没有用（对照）。

## 一条已经发生的"人工进化"

FUMO 确实经历过一次完整的进化闭环，只是每一环都是人做的。

**观察**——长任务探针显示子代理在 survey 任务上三次全部轮次耗尽、命中 0/5、输出 36~146 token。

**归因**——不是模型能力问题。证据是：换模型不改善；同一模型下换一种子代理配置就正常；日志显示模型把全部轮次用于读文件，最后一轮仍在调用工具。

**假设**——模型不知道剩余预算，所以无法收敛；最后一轮仍允许调工具，所以被硬截断时输出为空。

**改动**——剩余两轮时注入预算提示；最后一轮撤走工具，强制产出文本；新增 `Truncated` 标记。

**验证**——同一任务再跑两次：`truncated=False`，命中 3/5，输出 1403~1667 token。

这是一个标准的"观察→归因→假设→改动→验证"闭环。它完全符合书里描述的学习流程，唯一区别是每一步都由人执行，而不是系统自动完成。

## 如果要自动化，缺什么

书里描述的三层轨迹验证，FUMO 只有第一层的雏形。

**结果验证器**——判断"事情是否办成"。FUMO 有工具的成功/失败标记、回合的终态枚举、`Truncated` 标记，但没有"任务目标是否达成"的判断。一个回合返回 `Completed` 只代表模型停止了，不代表它做对了。

**过程验证器**——判断"是否以允许的方式办成"。FUMO 有权限模式和审批记录，但没有对动作序列的规则检查。比如"模型先删了测试再让测试通过"这种情况，当前不会被识别。

**质量验证器**——判断"是否让用户舒服"。完全没有。

三层里，第一层最容易做也最有价值：给每个任务定义可执行的验收条件，跑完后自动判定。FUMO 的探针已经用手写正则做了这件事（匹配预期事实），但只覆盖三个特定任务，不是通用机制。

## 一个反例：什么时候"进化"是噪声

FUMO 的开发过程中有过一次教训。早期版本为了让模型"更稳"，加了一批防御性默认值：固定 temperature 0.2、400k 字符压缩线、120 秒命令超时、100 秒 HTTP 超时。这些值的来源不是数据，是直觉。

真实长任务把其中三个证伪了：

- 100 秒 HTTP 超时杀死了长推理请求，表现为"模型无响应"；
- 400k 字符压缩线让压缩时机与模型真实窗口脱节，短窗口模型早就溢出了；
- 固定 temperature 让推理型模型直接拒绝请求。

这三个值当时看起来都是"合理的保守选择"。它们的问题不是错得离谱，而是**没有依据**——无法回答"它在什么任务分布下防住了什么"。

这条经验对自动进化同样适用：如果学习信号本身没有可靠的验收标准，自动调整提示词或参数产出的就是这类"看起来合理但没有依据"的改动。先有评估，再有进化，顺序不能反。

## 本章要点

- FUMO 没有自动持续进化，四种载体都只能由人更新。
- 三类证据已积累：性能 span（哪里慢）、会话历史（为什么）、对照实验（改得对不对）。
- 已经发生过一次完整的人工进化闭环，方法是"观察→归因→假设→改动→验证"。
- 三层轨迹验证只具备第一层雏形，缺任务达成的自动判定。
- 没有可靠验收标准时，自动进化产出的是噪声，不是改进。
