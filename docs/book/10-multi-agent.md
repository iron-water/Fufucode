# 第十章对照：FUMO 的两级协作

## 两种多 Agent，两个插件

书里按"上下文是否共享"划分多 Agent 协作。FUMO 正好在这条轴上各有一个实现，而且它们的定位被刻意分开。

| | Subagent | AutoDev Thread |
|---|---|---|
| 插件 | `workspace.subagents` | `automation.auto-dev` |
| 上下文 | 独立（可选 fork） | 独立，持久 |
| 生命周期 | 进程内，短 | 跨会话，持久 |
| 工作区 | 共享只读 / 临时 worktree | 持久 worktree + 租约 |
| 交付 | 结论或候选补丁 | 交付卡 + 真实 HEAD 对账 |
| 适用 | 探索、审查、小范围改动 | 需要协调的多任务开发 |
这个划分不是照搬书里的分类，而是从"什么该由父会话直接消化"这个角度切的。子代理的产出必须是父会话能一次性读完的东西；如果产出需要多轮审阅、需要跨会话等待，那就该升级为 Thread。

## Subagent：什么时候派发

书里给了一个判断多 Agent 是否优于单 Agent 的核心判据：协作过程是否引入了单个 Agent 在生成时无法获得的新信息。

按这个判据，FUMO 的子代理有一半场景是不成立的。让子代理"审查父会话刚写的代码"，如果它看到的只是同样的上下文，那就没有新信息，效果与父会话自己重读一遍相当。真正有价值的是：子代理去读父会话没读过的文件、跑父会话没跑过的命令、看父会话没看过的输出。

FUMO 的系统提示里写了这条判断：

> 适合派发：大范围搜索/定位、需要阅读大量文件才能回答、可拆成多个互不依赖的子问题、审查独立模块。
> 不要派发：单文件小改、已知位置的精确读取、需要保留完整上下文的连续修改。

这个提示是在一次实测后加的。在此之前，模型对任何任务都倾向派发子代理，成本上升而质量没有提升。

## 档位实验：一个被证伪的设计，和它留下的教训

FUMO 曾经有两个子代理档位：faster 与 stronger。这个设计在 2026-10-23 被归档，只保留一种行为。归档的过程比结论更有参考价值。

**最初的假设**是：stronger 应该"更彻底"——扩大取证范围、维护证据矩阵、允许嵌套派发子代理。直觉上，更多的检索和更强的结构应该带来更好的结论。

**第一次实测推翻了它。** 在同一份 8 点取证审计任务上：

| | 耗时 | 工具调用 | 覆盖 | 嵌套 |
|---|---|---|---|---|
| 旧 stronger | 585.6 秒 | 47 | 8/8 | 0 次 |
| faster | 90.5 秒 | 12 | 8/8 | — |

stronger 花了 6.5 倍时间，覆盖完全相同，嵌套一次都没触发。更关键的是，扩大取证并没有改变最终结论的质量。

**第二次尝试**：改成"同范围取证 + 程序化引用校验 + 仅在发现坏引用时派定向校验子代理"。成本回到同一量级（56.3/94.3 秒，30/28 次工具），引用有效率 33/36 与 16/18——但**没有稳定优于单遍模式**，修正列表也没有改变最终结论。

**结论**：没有可证明的能力增量支撑第二个档位。产品只保留一种行为，采用原 faster 的早停取向：先用 grep/glob 定位，再读必要片段，证据足够就停，未验证项标注。

这个实验对应书里的判据：多 Agent 优于单 Agent 的前提是**引入新信息**。扩大取证范围不是新信息，只是同一批信息的更多副本；证据矩阵不是新信息，只是已有信息的重新组织。真正的新信息来自执行反馈、视觉反馈、外部工具验证——而这三样在纯只读检索任务里都不存在。

**嵌套被保留为显式能力**，而不是档位差异：只有代理定义显式声明 `subagent` 且未到 `maxDepth` 时才开放。内置 `explore` 不声明，避免默认递归和成本失控。这是一个更保守的选择——能力存在，但需要用户主动配置。

## 一个更重要的发现：循环设计压过档位设计

档位实验期间还暴露了一个更基础的问题。修复前的 faster 在 survey 任务上三次全部轮次耗尽、命中 0/5、输出 36~146 token；修复后同样的 faster 命中 3/5、输出 1403~1667 token。

模型没变，档位没变，变的只是循环的预算提示与最后一轮工具策略。这说明**在 Harness 层面，循环设计的收益可能远大于档位分化**。花力气做第二个档位，不如先把预算感知、强制收尾、状态台账这些基础做对。

这条经验也解释了为什么档位实验最终被归档：当基础 Harness 还有明显缺陷时，档位差异会被噪声淹没，测不出来。

## 共享上下文的取舍

书里对比了两种角色转换方式：替换 system prompt（`transfer_to_agent`）与加载 Skill。前者改变请求前缀，缓存失效；后者保持前缀，内容追加到轨迹末尾。

FUMO 的 Subagent 走的是第三条路：**完全独立的上下文**。子代理有自己的 system prompt、自己的工具白名单、自己的历史。父会话只收到最终结论。

这个选择的代价是信息不连续——子代理不知道父会话之前做了什么，除非显式 fork 或者通过 `context` 参数传入线索。收益是隔离：子代理的大量中间检索不会污染父会话的上下文。

`context` 参数是为此加的：

```json
{
  "agent": "explore",
  "prompt": "定位入口",
  "context": "入口在 src/Program.cs:42，已经排除 config 目录"
}
```

父会话把已确认的线索传下去，子代理不必从零发现。这个设计对应书里"共享上下文"模式的优点（信息不丢失），但用显式传递代替了隐式继承。

## 失败模式：FUMO 遇到过的三类

书里列了六种多 Agent 失败模式。FUMO 实际遇到过其中三类。

**并发冲突。** 多个 patch 子代理同时创建 worktree 会争用 `.git/worktrees` 元数据。FUMO 的解法是只串行化创建动作（`SemaphoreSlim`），运行本身仍然并行。

**错误的级联放大。** 父会话把一个模糊任务派给子代理，子代理基于错误假设完成，父会话直接采信。缓解手段是要求子代理区分"已确认（有文件:行号证据）"与"推测"，并在结果里标注是否因轮次耗尽而截断。

**循环失控。** 嵌套子代理如果没有深度限制会无限递归。FUMO 的 `maxDepth` 默认是 1，即 root 之下只能再派一层。

另外三种（同质趋同、互相扯皮、理解债）在 FUMO 的形态下不容易出现，因为没有多轮辩论机制，子代理之间不通信。

## 一个诚实的空缺

书里花了相当篇幅讨论 Agent 社会、经济博弈、跨组织协作。FUMO 在这些方向上没有任何实现，也不打算做。

原因不是技术难度，是产品定位。FUMO 是一个桌面 Coding Agent，它的多 Agent 能力服务于"把一个大任务拆开做完"，不服务于"让多个 Agent 自主协商"。后者的价值在开放搜索空间（书里举的漏洞挖掘例子：45 个 Agent 用 2700 万 token 找到 266 个漏洞），而 Coding 任务的搜索空间是收敛的——你知道要找什么，只是还没找到。

这个判断可能是错的。如果将来 Coding 任务也变成开放搜索（比如"找出这个代码库里所有的安全问题"），那多 Agent 协商就会有价值。当前的证据不支持这个方向。

## 本章要点

- FUMO 有两级协作：Subagent（短、独立上下文）与 AutoDev Thread（长、持久 worktree）。
- 派发判据是"是否引入新信息"；同上下文重读没有价值。
- 档位设计被证伪并归档：扩大取证不是新信息，实测无能力增量。
- 循环设计的收益可能远大于档位分化，基础 Harness 有缺陷时档位差异测不出来。
- 嵌套保留为显式能力，需代理定义主动声明，内置代理不声明。
- 独立上下文用 `context` 参数显式传线索，代替隐式继承。
- Agent 社会类协作不在 FUMO 的定位内，当前证据不支持。
