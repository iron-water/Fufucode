## [轨道C] 回合结束的 UI 同步约定（集成时 A 也会遇到）

- 2026-09-28：IChatSession.Event 可在任意线程引发（冻结面已写明），外壳统一在订阅侧用 Dispatcher.UIThread.Post(...) 封送到 UI 线程；Avalonia 12.1.3 实测 Post 不带优先级时默认 DispatcherPriority.Default（=0）。
- 关键时序：会话实现通常在后台线程先 Raise 终态事件（MessageFinished / TurnSettled），之后才把 Activity 置回 Idle。因此"观察到 Activity == Idle"只保证终态事件**已入队** UI 线程，不保证回调**已执行**；此时读取时间线会看到缺失的助手消息（轨道 C 自测早期偶发失败"正常回合未产生助手消息"的根因，非逻辑错误）。
- 约定：任何"等回合结束后再读 UI 状态"的代码，在观察到 Idle 后必须先排空 UI 队列——轨道 C 用 `await Dispatcher.Yield(DispatcherPriority.Background)`（实测 Background=-2 严格低于 Default=0，dispatcher 按优先级出队，保证已入队回调先跑完）。该修复依赖优先级偏序、不依赖机器时序。
- 推论（供 A 集成时参考）：TimelineViewModel 的终态事件（MessageFinished / SessionError）会立即触发一次同步刷新，但若 IChatSession 的真实实现在把 Activity 置 Idle 后还异步投递了别的终态事件，订阅者仍按上述约定排空，不要假设单次回调即终态。

## [轨道B] M5 交互面清单：extension_ui_request/response 冻结契约（Pi 0.87.1 实测）

> 实测来源：`scripts/demo-verify/`（真实 Pi RPC 模式 + stub 模型，7/7 通过）+ `dist/modes/rpc/rpc-mode.js` 源码。此清单是 A（Core 路由）与 C（弹窗映射）的对接契约；后续改动与清单冲突时须在此追加协调。

### 必须应答的 method（响应字段决定返回值）

| method | 请求字段 | 响应字段 → 返回值 |
|---|---|---|
| `confirm` | `id, method, title, message, timeout?` | `{cancelled:true}` → `false`；`{confirmed:bool}` → bool；其他/超时 → `false` |
| `select` | `id, method, title, options[], timeout?` | `{cancelled:true}` → `undefined`；`{value:str}` → str；其他/超时 → `undefined` |
| `input` | `id, method, title, placeholder?, timeout?` | 同上，value 为文本 |
| `editor` | `id, method, title, prefill`（**无 timeout 字段**） | `{cancelled:true}` → `undefined`；`{value:str}` → str；**不收其他键** |

- 响应解析顺序：`cancelled:true` 优先；`confirmed`/`value` 取其一；**两个都缺省即默认值**（confirm→false，其余→undefined）。应答未知/已过期 id 被静默忽略。
- **`editor` 没有 timeout**：请求记录不带该字段，Pi 不设超时——host 必须应答（答 cancelled 也行），否则 promise 永久挂起。实测：editor 挂起时 select/confirm/input 已按各自 timeout 自决。

### 免答的 method（fire-and-forget，无 pending 记录）

`notify`(`message, notifyType`)、`setStatus`(`statusKey, statusText`)、`setWidget`(`widgetKey, widgetLines, widgetPlacement`)、`setTitle`(`title`)、`set_editor_text`(`text`)——均无需响应；给它们发响应会被静默忽略。

### 实测行为（供 A/C 对接）

- **`timeout` 字段语义**：仅出现在 confirm/select/input 请求中；到时 Pi 侧自动 resolve 默认值并**不再等响应**（未观察到任何超时通知帧）。host 不应假设超时会通知它。
- **非阻塞输入分发**（`handleInputLine` 以 `void` 分发）：对话框挂起期间后续 stdin 帧仍被处理——实测 editor 挂起时 `get_commands` 正常应答。
- **`/命令` 的 prompt 响应时序**：扩展命令 handler 在 `session.prompt()` 内部 await，`preflightResult(true)` 在 handler **完成后**才发——dialog 挂起时 prompt 响应不返回。host 不得先等 prompt 响应再答对话框（会造成死锁，dead-lock-free 场景实测验证）。
- **`widgetLines` 只支持字符串数组**：组件工厂与 `setWidget(undefined)` 不产生任何帧（实测仅数组发出 `widgetKey+widgetLines` 帧）。
- **扩展命令入口**：RPC 模式下 `prompt` 消息以 `/` 开头即执行 `getCommand` 匹配；`_throwIfExtensionCommand` 阻止向 stream 排队 `/` 命令（steer/follow_up 会 throw）。
- **未知 method**：不存在——所有 method 均为 Pi 内部枚举；host 收到未知 method 时安全做法是记录并忽略，不应答（不产生 pending 副作用）。
- **连接丢失**：Pi 进程退出即所有 pending 请求失效；扩展侧一律视为拒绝（fail-safe）。

### 已知限制（如实记录）

- RPC 模式不支持：`custom()`、组件工厂（`setWidget`/`setFooter`/`setHeader`/`setEditorComponent`）、`getEditorText`（同步返回 `""`）、`getEditorComponent`、原始终端输入 `onTerminalInput`、工作指示器（`setWorkingMessage`/`setWorkingIndicator`/`setHiddenThinkingLabel`）。
- `editor` 无超时、不支持 `opts`；`select`/`input`/`confirm` 支持 `timeout` 与 `signal`。
- 对话框按扩展顺序串行 await；同一扩展内并发 `ctx.ui` 调用会各自排队（无并行对话框锁）。

## [轨道A] A13 契约包：思考等级、UI 审计、只读 diff、fork 谱系与元数据 schema 3

- 2026-10-02 **成功不等于生效**：`set_thinking_level` 对不支推理的模型被 Pi 静默钳制且仍返回成功（D-8）。Core 因此提供 `get_available_thinking_levels`（`ThinkingLevelAvailability`），并在应用保存的等级未生效时抛出**指明可用等级**的错误，而不是笼统的“未选择”。UI 应以可用列表驱动控件，而不是假设等级总可设。
- **扩展 UI 留痕**：`PiDiagnosticEvent` 增加可选 `Outcome`。每个扩展 UI 事件都记 `extension_ui_request`（方法 + 对话 id），应答后记 `extension_ui_response`（value/confirmed/declined/cancelled/expired/closed/notified/ignored + 耗时）。对话正文、标题、选项文本一律不进日志。这样 D-6 那类“某次 write 的审批到底是谁给的”可事后审计。
- **只读不得有写副作用**：`sessions list` 原本会用 `GetOrCreateProject` 把项目写进元数据，改为新增 `TryGetProject` 只读查询；`project` 输出规范化后的规范路径，另加 `projectId`。
- **patch/hunk 只做只读**：`DiffQuery` 只解析 `git diff`，明确不实现还原 / stage / 提交；`truncated:true` 必须如实暴露，不得把截断的 hunk 当完整差异；numstat 的 `--`（二进制）为 null，不得当 0。
- **fork 的锁交接顺序**：Pi 的 `fork` 会把**同一进程**重新绑定到新 sessionId/sessionFile。Core 先取子会话锁再交还父会话锁，保留父会话行并写入 `parent_session_id`/`fork_entry_id`/`forked_at_utc`。父文件字节不变只是**证据**（`ParentFileUnchanged`），不是 Pi 的承诺。父会话对象交出 Pi 所有权后 dispose 不得杀进程。
- **元数据 schema 2 → 3**：新增三列均先 `PRAGMA table_info` 探测再 ALTER（避免“列已在但 user_version 落后”报重复列）。迁移前备份文件名随之变 `desktop.db.before-v3-*`。**跨版本回退 drill 与重包由 F/协调者接手**：schema 3 一旦落到用户数据目录，旧版 App 会因 `version > SchemaVersion` 拒绝打开。

## [轨道D] Wave5-R4 阶段2：OS 系统通知 toast 结案（本机环境限制，不再投入）

- 2026-10-02 **采纳路线 c 回退，阶段2 正式结案**：未打包 Win32 应用发 toast 必须有 AUMID，且开始菜单需存在带该 AUMID 的快捷方式；本机无法完成该注册，判定为**环境限制而非实现缺陷**。取证：`SHGetPropertyStoreFromParsingName` 对 `.lnk` 与普通 `.txt`、在无头自测进程与独立 PowerShell 进程共四种组合下**一律返回 `E_NOINTERFACE (0x80004002)`**；IID 已核对为字面量 `886D8EEB-8CF2-4446-8D02-CDBA1DBDCF91` 一致，排除传参错误。对照下 `IShellLinkW`+`IPersistFile.Save`+`GetPath` 全部 `hr=0`、`.lnk` 落盘且回读正确——即"建快捷方式"通、"给快捷方式写 AUMID 属性"不通。跳过快捷方式仅 `SetCurrentProcessExplicitAppUserModelID` 后直接 `ToastNotificationManager.CreateToastNotifier()` 抛 `COMException`。本轮及后续**不再在此方向投入**。
- **纠正一条流传的任务书前提**：`Microsoft.Toolkit.Uwp.Notifications` 7.1.3 的 `ToastNotificationManagerCompat` **不会**自动创建带 AUMID 的开始菜单快捷方式——实测其全部 TFM 变体二进制内不含 `Start Menu`/`IShellLink`/`.lnk` 字符串，只有 `Aumid`/`AumidAndComServer`/`AumidFromPackageManifest`；7.1.x 的 `DesktopNotificationManagerCompat.RegisterAumidAndComServer<T>` 走 COM LocalServer 注册（写注册表 + 需 activator 类），面更大。另注：引该包会传递带入 `System.Drawing.Common` 4.7.0，restore 报 **NU1904 严重漏洞 GHSA-rxg9-xrhp-64gj**（修复版本 ≥4.7.2/5.0.3），须显式抬版本而非抑制警告。
- **保留可复用结论**：TFM 升 `net10.0-windows10.0.19041.0` 与 Avalonia 12.1.3 兼容（单改后 build 0 警告 0 错误、selftest 0 失败），系统 WinRT 投影 `Windows.UI.Notifications`/`Windows.Data.Xml.Dom` 可直接用，无需第三方包。AUMID 按安装路径哈希派生（同路径稳定、不同安装互不覆盖）、toast 内容只含事件名+会话标题且做 XML 转义、activation 用 `fufucode-session=<id>` 走命令行回读、OS toast 与页内通知共用同一 `proactive` 判定（6 场景实测）、偏好开关需兼容 v1 旧文件——这些均已实测通过并随回退移除，需要时可重建。
- 根治方向（不在 D 轨）：给应用加 MSIX/稀疏包标识（属轨道 F），或换正常 Windows 正式版构建复测本机是否为 Insider 构建（10.0.26300）特有故障。

## [轨道D] Wave5-R4 阶段3：队列条编辑/删除按 Core 能力边界收敛，界面已就位待 A-R4-1

- 2026-10-02 **不硬修 Core**：`IChatSession` 只暴露 `QueuedCount`，无任何队列变更方法；`ChatSessionCoordinator` 的 `_queuedTexts` 为私有状态，入队只在 `SendAsync`（:256）、出队只在投递时按文本 `IndexOf→RemoveAt`（:477-478），唯一显式清空是 `clear_queue`（:359）且绑定在「停止」语义上（会连带中止当前回合）。而 `InputViewModel.SyncQueue`（:252）对 `QueueChanged` 载荷做**整体 Clear+重填**，即界面 `QueuedTexts` 永远是 Core 的镜像——任何"本地删除"都会被下一条 `QueueChanged` 覆盖、被删条目复活。该脱节场景已写成回归断言锁住，不是推测。
- **本轮取舍**：队列条每行的「编辑」「删除」入口与真实命令（编辑=回填输入框并移除、删除=仅移除该条；已有草稿时追加不覆盖）**全部就位**，但对 Pi 已持有的条目一律 `IsEnabled=false` + tooltip 说明受阻原因，并**指向今天真正可用的路径**（按「停止」整列清空并退回输入框再编辑），避免把用户引向死胡同。宁可交付"看得见的边界"，不做会复活的伪删除。
- **待 A 轨接口后一键点亮**：需要 **A-R4-1** —— `Task<bool> TryRemoveQueuedAsync(string text, int occurrenceIndex)`（可选 `TryReplaceQueuedAsync`），语义要求：仅作用于**尚未投递**的条目，命中失败返回 false，成功后必须广播 `QueueChanged` 让镜像收敛。届时 D 侧只需把预览项标记为本地持有（`QueuedItemViewModel.IsLocallyOwned=true`），按钮即自动可用、tooltip 自动清空，无需再改界面或命令代码。
