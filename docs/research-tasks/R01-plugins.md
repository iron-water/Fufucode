# R01 Pi 插件与前端开放接口

遵守 [共同协议](README.md)。允许写入：仅 `docs/research-results/R01/`。优先级最高。

## 需求

Fufucode 使用 Avalonia 和官方 Pi RPC，不移植内核。用户受 deepseek harness（dsh）“一切皆插件”、聊天中热插拔/热更新启发，希望先明确 Pi 能力，再设计独立的前端功能插件。终端可安装或不安装，但三栏停靠和中央对话宿主不能由插件替换。

## 必答问题

1. 先确认本仓实际 Pi 包名、版本、RPC 基线，再绘制 API 能力表：extension、tool、command、skill、prompt template、package 各自生命周期。
2. RPC 下 extension UI 的请求/响应、取消、通知、状态、widget、自定义 UI 等哪些支持、忽略或不支持？逐项用当前版本证据说明。
3. 会话中加载、卸载、reload、热更新的真实接口和限制是什么？运行中工具、已有上下文、依赖、失败回滚如何处理？不能把 TUI 能力直接当 RPC 能力。
4. Pi 扩展如何映射前端菜单、权限确认、表单、状态和工具输出？比较应用自有 bridge 扩展与官方接口直接适配，不虚构命令。
5. 将 Pi 扩展与 Avalonia 功能插件分成两层：终端、文件预览、浏览器可选模块如何注册页面、保存布局、声明依赖、卸载及迁移设置？卸载不应破坏核心三栏宿主。
6. 比较内建可关闭模块、进程内插件、进程隔离插件的成本与信任边界；研究包来源、签名、权限、兼容版本和崩溃隔离。
7. 先核实 dsh 项目身份及官方来源；不唯一时列候选、标未证实，仍完成 Pi 研究。对比热更新机制，不照搬宣传语。

## 验收与交付

交付 API 能力矩阵、生命周期图、前端边界草案和最小 PoC 方案。区分“Pi 已提供”“bridge 可补”“仅前端负责”“无法实现”。推荐先做的一个增量及行为验收，明确无需现在制作通用 SDK。
