# 对话驱动全自动工作台：差距核查与建议

日期：2026-10-15；源码观察基线main `81c18c24143115e9b8559934f8c5b01dee7ac5d5`。只读源码/公开文档研究，未运行产品或付费模型，未把历史测试计数算作本轮通过。运行中仓库会继续变化，实施前复核相关文件。

## 判断

Fufucode缺的主要是“从目标持续组织开发”的项目级控制闭环，而不是再画一张图或重写全部持久化。现有状态库、任务版本、真实运行身份、停写/HEAD门禁及部分审核应保留。主控对话作为用户入口与语义决策者，程序负责可靠执行和继续推进；主控不靠无限增长的聊天记录记住一切。

用户本轮明确要求把这一流程作为默认，替代旧工作台。新权威设计见 `docs/design/conversation-workbench-v4.md`，前端见同目录 `conversation-workbench-v4-ui.md`。旧文档全人工默认、先连数据库/填工作包的用户流程被取代，旧状态和有效成果不因此作废。

## Codex基准应怎样理解

公开可核实的能力：App Server提供线程开始/恢复、turn开始、活动turn steering、流式事件和终态；终态completed/interrupted/failed要分别处理。它是可编程会话控制接口，不是本项目全部自主规划/验收/后台恢复能力的完成证明。[官方App Server](https://learn.chatgpt.com/docs/app-server)

Codex管理Git工作树和设置环境，可为独立任务准备不同checkout；忽略文件/本地配置不会无条件自动出现在新工作树中。[官方工作树](https://learn.chatgpt.com/docs/environments/git-worktrees)、[本地环境](https://learn.chatgpt.com/docs/environments/local-environment)

桌面本地定时任务要求电脑开机、应用运行。不能由此宣称关闭GUI仍有独立后台服务或关机能继续执行。[官方定时任务](https://learn.chatgpt.com/docs/automations)

本项目已经实践的“主控创建执行会话→agent主动回传→主控审查/集成→补漏”包含用户提示词和定时组织，并非Codex自身默认的自主项目调度。已发生过执行者只给最终卡但未发消息、主控未立即继续的实例；Fufucode产品应通过终态接收/持久消息/协调任务修掉这类薄弱点，而不是复制提示词期待模型永不遗漏。

## 逐项差距（P0为首个可交付闭环必需，P1为默认无人值守完整交付必需）

| 项目 | 当前证据 | 缺什么及建议 |
| --- | --- | --- |
| P0 自动模式 | `AutomationStore.Control.cs`的SetMode遇Automatic直接抛`Automatic policy is not enabled.` | 不是改枚举/删除异常；实现有效委托、自动决策来源与项目协调器后，才启用默认自动入口 |
| P0 目标到工作包 | `AutomationControlViewModel.Creation.cs`要求手填Goal/Scope/Acceptance/Harness/Model | 主控对话生成结构化提案，程序校验目标覆盖、依赖、权限，再在委托内提交；用户不手抄计划 |
| P0 工作树分配 | `GitWorktreeService.CreateAsync`已能git worktree add；`ControlIntentConsumer`只验证预先存在的目录/注册线程 | 复用Git工具，补意图/回执/孤儿资源对账、起点与环境准备、资源所有权，串成创建线程的受管事务流程 |
| P0 原生会话控制 | BatchAdapters提供批量执行和原会话恢复；Capabilities是resume/streaming=true、approval/cancel/attach=false | 原生C#及各后端插件扩展实际能力描述；需要活动输入/审批时采用已验证长连接适配，不把CLI批处理接口假装全能力 |
| P0 并发执行 | `BackgroundHost.DrainAsync`取NextQueued后await RunOneAsync，单消费路径串行 | 单宿主不等于单worker；持久运行槽和冲突检查支持默认两个受限worker，M/集成同项目串行 |
| P0 交付接收 | `DeliveryReceiver`已有终态/HEAD/身份校验 | 接收后必须事务写入可恢复通知/协调事件；缺卡/坏卡也形成异常待办，不等模型主动send |
| P0 跨线程消息 | 状态层有任务事件，但本轮未在所核控制链找到完整持久inbox/outbox与消费推进闭环 | 将发出/投递/确认/处理/未知分开，绑定线程/任务/版本，消息去重、主控忙时排队；不是直接拼字符串到UI |
| P0 主控继续 | 宿主明确只消费已接受请求，注释No AUTO；Consumer不生成线程 | 增项目协调器：待审→修复/整合→解锁→派工；空闲待目标、暂停、全部阻塞、未知分别停在可解释状态 |
| P0 前端入口 | 当前AXAML先连接数据库，提供全人工/半自动、表单、待办与Canvas | 新主控对话+项目运行概览为首屏；计划由系统生成，图是工作对象视图，数据库和回执退到诊断 |
| P1 成本/上下文 | 当前模型与线程保存，用户纪律在prompt/AGENTS中 | 程序落实预算/并发/重试上限；主控按需唤醒、上下文有界打包、模型或工具不可用显式阻塞 |
| P1 后台和自启 | BackgroundHost已有独占slot、恢复、TCP观察/命令，GUI本地读取AutomationStore | 复用独立宿主，GUI写命令统一由宿主执行；补用户级后台生命周期/登录自启/状态重连，不要求手输DB |
| P1 集成与终验 | 当前有accepted/integrated/部分审核、控制集成记录 | 自动集成必须先受控候选验证、main租约和实际Git结果；项目终验绑定目标与候选版本，不把全部idle判完成 |
| P1 内核/插件 | 原生C#内核和插件市场已立新范围，当前原生类仍回显雏形 | 工作台默认选择NativeCSharp但缺能力应显示未就绪；开发可用已授权插件验证接口，完整生产验收不能绕过原生Node-free目标 |
| P1 迁移 | 有旧JSON、SQLite与外部组织流程；旧mode含manual | 版本化迁移只改变新建默认和新工作流；保留已有人工/暂停/在途身份，不能新旧双调度/复制任务后并跑 |

这些为指定源码路径的静态判断，不声称穷尽仓库所有工具，也不以未找到某符号证明任何模块从未存在。M可用实际新实现反证并更新差距，不删除原观察基线。

## 我的实施意见

1. 核心状态/身份/恢复复用；前端和项目组织策略替换。不要重做U1数据库，不把新服务变成第二个调度器。
2. 先交付一个“对话目标→真实worktree/worker→有效交付→M审核→真实候选集成→自动下一任务”纵向包，同时处理缺卡、主控忙、暂停、重复事件。没有闭环就不要先堆十种仪表盘。
3. 第二个完整包补跨后端能力、两个worker并发、预算、后台/登录启动与恢复，完成后才把新安装交付称为默认全自动可用。交互原型和后端可在共享投影契约冻结后并行。
4. 普通交付只在有新证据或异常时调用M；CHECK/专家是按需活动，不是每次必须全员会签。不要用最贵模型进行机制验证。
5. 结果可信度优先于“看起来一直在工作”。每个停顿都展示原因、责任方、下一次检查；坏交付不能当完成，重复接管不能当修复。
