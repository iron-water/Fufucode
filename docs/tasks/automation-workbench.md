## 流程图是主要交互

2026-10-10 用户进一步明确：**图节点是对话线程，一线程包含多个任务，任务又可分部分交付/部分打回。**这取代 U0 先前“步骤作节点”的示例。CLI 既有一任务一会话运行仍是原记录，不因此迁移或接管活跃会话；新产品的 Thread/Task/DeliveryPart 契约按下文设计。

- 大层级：项目 → 主控/首轮/后续阶段 → Harness 分组 → 对话线程。线程卡内部列任务身份、状态、进度和局部修复；验收门属于 M 线程的任务，不假称另一个会话。
- 示例图包含9个线程、50个任务、51条任务端口连线，涵盖 D0–D6、O1–O7、S1/S2、M0、U0–U3、M内G0/G1/G2/G3/QV/R，以及后续D8/D9/S3/O8。任务是示例归组，不冒称这些线程已创建或重新派工。
- 连线连接线程内部的具体任务端口。交付/打回绑定 threadId、taskId、partId、runId、HEAD、decision；只改变该部分状态和修复轮次，不清空全线程、其他任务或已集成部分。
- 数据层增加 Thread → 多个 Task → 多个 DeliveryPart/Revision；已记录的决定不可覆盖，回修产生新运行/新部分版本。依赖按所需任务部分与实际集成证据判断，不能因线程总体显示“有完成项”而解锁。
- 同线程持有固定 harness、模型、保存会话与工作树。任务续接必须属于批准范围；同线程命令串行，一个受管会话写入者。子任务并发按独立所有权/工作树与真实子代理关系管理，不把多个任务行当作多写入授权。

- 开发闭环发生在线程之间及其内部任务：需求/验收 → M 任务拆分 → 执行 → 停止后部分交付 → 本地核验/排队 → M 串行审核 → 部分接受/打回 → 共享接线 → 独立验证 → 依赖解锁。动画不把这些步骤再画成独立线程节点。
- 项目图表达任务依赖与实际门禁；沿用主线 Mermaid 的任务身份和边，不由动画自行推导授权或验收。当前 HTML 提供与自动开发有关的依赖子图，未宣称覆盖完整排期图。
- 点击节点进入任务卡、执行会话、交付、审核决定、集成证据或失败恢复；这些内容属于节点上下文，不另建独立仪表盘作为主入口。详情在图内/图下展开，适合功能区的可变宽度。
- 节点状态与流动连线随真实事件更新。演示播放/暂停/速度与真实任务暂停/停止必须区分；动画暂停不暂停后台工作。真实事件流与历史回放使用同一身份/游标，回放不产生执行副作用。
- 支持缩放、适应视图与减少动态效果偏好。动画只表达已知状态；空闲不制造进度，不持续调用模型。异常冻结直接标在对应门房/审核节点。
- 后台设计由 M 依据已验证机制负责，用户无需选择内部协议/存储/进程方案；重大产品行为、授权与费用边界仍明确展示。

## 阶段与门禁

当前开发流程已有真实 CLI 控制台 `http://127.0.0.1:18765`，由 Windows 任务计划程序独立启动。只读取批准 workflow 的受管线程，不接管未知会话。自动模式沿用现有依赖、路径冲突调度、最多2个worker、串行M审核及单写入集成。默认调优未启动任务优先免费 `devin/swe-2`，不自动升级已启动任务。手动模式暂停新派工/审核，可编辑模型、执行依赖、集成依赖；新增任务仍需允许路径和三个真实契约文件。已启动任务、门禁及运行身份不可改。

保存草稿不改批准计划。应用仅在 M ready、受管worker停止、workflow空闲/暂停时执行：暂停门房、停止workflow、走 `agent-workflow.ps1 -Mode Approve`，成功仍保持暂停；恢复为独立操作。失败按原始字节恢复计划/审批，不明apply保留claim拒绝重发。UI不写review.json或执行任意shell。真实模式禁用演示；现有v1仍整项交付。新增部分审核/多任务会话及原生tab继续按下表验收。

## 产品契约

用户新增[节点人类变更卡](human-change-control.md)：从线程内具体任务/步骤追加验收要求，或停止后修订；固定M保留最终审核权。当前撤销/版本重建入口只支持部分基础能力，意见收件、M确认、需求版本审核绑定及过期决定阻断尚待U1/U2实施，不把保存元数据当成已经接入审核。

1. Project、Task、Run、Delivery、ReviewDecision、Integration 分开建模。固定保存 harness/backend、native session、model、worktree、原始基线、允许路径、任务图与预算；子代理有 parentRunId，父任务须实际收回结果。
   新产品补充 Thread 与 DeliveryPart/Revision。Thread持有多个Task，一个Task可有多个部分；task/part各自维护进度、交付版本和修复轮次。部分打回不可改变同线程其他Task/Part或历史已接受决定。现有v1脚本尚不自动支持该新增结构，U1/U2须提供版本化适配与独立验收，不能把HTML部分打回当成生产协议已升级。
2. 独立后台宿主拥有受管会话写入。窗口是观察/控制客户端；关窗、停止宿主、暂停调度是三个不同操作。电脑睡眠不执行；重启后恢复持久状态，不假称进程存活。
3. UI 命令带 commandId；事件带单调游标。重连先快照，再补齐；重复命令不重复启动任务。实际接口由 U1/D5 交付冻结，不虚构后端 RPC。
4. 空闲只运行本地事件监督。仅 delivery.received 且缺 review.decided 进入候选；读卡前再检查 completed_pending_review、执行者已停止、真实 HEAD 与卡一致。坏卡/变更 HEAD/活跃写入者都不能接受。
5. M 审核串行，积压可多份。决定仅 accept/rework/blocked/defer，现有脚本桥接必须经过 agent-queue.ps1 -Mode Review；新产品入口必须保持同样的校验与原子落盘，不允许 UI 直接写 review.json。
6. module_ready 可接受，接线归 M。只有精确接受 HEAD、共享接线提交及独立验证记录齐全，才完成 Integration 并解锁相应依赖。接受不解锁“已集成”依赖。
7. 打回回原工作树、原模型、原保存会话。恢复前核对身份、活跃进程与继承改动；不自动新建工作树或升级模型。已知单项失败不妨碍独立任务；共享 M 状态不明则冻结自动投递。
8. 投递前持久 claim。启动后掉线、不明状态、崩溃均停止自动重发；只有终态与有效决定身份对得上才本地对账。不承诺对模型服务/任意外部工具的 exactly-once 副作用。
9. 单个主线集成写入者加租约与提交前核对；受管锁不能阻止未知用户进程。检测冲突则停止本次集成，保护用户修改。审核、集成、失败、暂停原因和下一步必须有本地记录。
10. 批准任务图与授权边界必须是宿主可校验的数据。登录、采购、push、部署不包含在自动执行中；模型费用、重试和升级单独受控。明确 OS 权限与任务协议限制，不能把完整权限 prompt 说成系统沙箱。

## 必须实际通过的验收

- 无待审事件零模型调用、重复事件零新增调用、多份积压串行审核、同一主线只有一个受管集成者。
- 正常模块接受及“明确打回 → 原会话修复 → 重新交付 → 接受 → 共享接线 → 独立验证 → 下游解锁”。跨 harness 且含真正收回的子代理。
- 关闭全部 GUI/交互 CLI 后宿主与 worker 继续；重开只观察原任务。睡眠恢复、宿主崩溃与登录重启分别验证，不以重载 HTML 代替。
- 坏卡、HEAD 变化、活跃写入者、模型失败、漏事件、断线和不明投递；重启恢复积压、不重发不明投递；日志足以独立复核。
- 暂停新派工/审核与停止执行者分开；凭据脱敏、审批有效性、费用界限和原生焦点/缩放/键盘实际检查。

既有脚本夹具与真实 D4 子任务是机制基线。产品接线验收必须绑定新产品提交、构建、宿主和原生界面证据。
