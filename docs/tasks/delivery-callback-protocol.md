## 执行者回传规则（加入新派任务包及正常返工/续接）

1. 完成必要验证与提交，主动生成完整交付卡并保存在本任务记录；保证所有编辑、Git及构建写入进程结束，此后不再修改工作树。
2. 使用M派单绑定的真实workerThreadId/taskId/runId或turnId、baseSha、deliveryRevision和deliveryHead，生成稳定eventId。修复再交付使用新revision；同一交付重试保持原eventId，不因“时间变化”创造新交付。缺身份时报告缺失，不编造。
3. 经授权且有消息工具时，用send_message_to_thread向固定主控发送一次交付通知，附完整卡和证据路径、实际HEAD、版本、eventId。不能把卡里的writerStopped=true当作主控独立核查的替代。
4. 记录投递成功/失败/结果不明。未拿到确定成功不能写delivered；结果不明不盲目重发，交两小时对账。工具缺失/失败保留卡待补扫，不无限等待，不假装调用CLI等价入口成功。
5. 最终回复仍按本任务格式给delivery.card JSON并结束本轮，不等主控回复、不继续接任务、不主动循环发送“收到”。通知在最终回复之前发出，主控当时可能看到执行轮次仍inProgress：消息只能作为待收事件。

需协调/真实阻塞时可发相应事件，不把它当终态交付，不释放任务占用槽。普通进度不发回传以免频繁唤醒。

## 主控收取与去重

- 通知只触发核查。先按eventId/worker/task/run/revision/HEAD对账，重放不重复审核/集成/派单。
- 再用wait_threads等核实worker本轮completed且无活跃写入者，实际HEAD与交付一致。仍运行则登记待收取，在已有监督周期收尾时再次核对或等两小时补扫；不能读半成品并将预告当有效交付。卡只写“停写”但状态未结束，不立即整合。
- 使用现有单写入租约与台账。主控忙时回传可能排队/成为后续输入，投递不代表审核已发生；不并行启动第二主控，不抢占/打断未知写入者。
- 明确accept/rework/blocked/defer及integrationStatus。accept不等于完整接线/验收；依赖门未过不派后继。最多两执行者规则不变。
- 本次处理完成后主动给下一步操作卡；主控不向执行者发送无必要“收到”回执，避免相互唤醒循环。只发送既有授权范围内的明确返工/协调工作。

## 效果判断与验证边界

原每小时收取方案的单次额外等待约0到60分钟，均匀分布假设下平均约30分钟。改为两小时纯补扫时，上界约120分钟、平均约60分钟；正常回传成功时不必等补扫。主控活跃时已有wait_threads/主动继续可能提前收取，真实当前收益会小于该上界。回传减少等待下一个时点，不减少实现、验证或集成本身耗时。

不承诺秒级唤醒或总体倍速，消息投递/主控忙碌/最终轮次结束仍有延迟。若保持每两小时兜底再加事件，主控唤醒次数可能增加、token可能增加；后续有真实回传可靠性和成本数据才考虑降低兜底频率。

本机执行需要电脑开机、应用运行。睡眠/退出/异常停机漏掉的回传靠持久交付记录和恢复后的补扫对账，不能声称关机仍能开发。桌面并无已证明的“任意执行线程完成触发heartbeat”开关：本方案使用消息回传加现有heartbeat，不把外部应用事件任务混作线程完成回调。
