# 可浮动页签、辅助栏与三处通知

2026-10-11，依据用户本线程最新确认。此要求取代旧独立浮窗形态及“状态栏默认显示”的建议。现有Windows设置导航和左右辅助栏布局保留，增量扩展。

## 明确的产品要求

- 每个功能页页签可独立浮动，整个辅助栏也可连同多个页签浮动；复用已有左/右/底部停靠模型，不做第二套业务页面。
- 取消独立“浮窗”产品入口，将通知、辅助对话等现有内容迁回通用功能页与辅助栏；已有侧聊会话身份和草稿不能丢失。
- 通知必须保留三个可配置提示地点：应用内浮层、Windows原生通知、辅助栏中独立通知功能页。第三处承接原浮窗通知提示，辅助栏浮动后仍能提示；不是仅给页面导航入口就算迁移完成。渠道独立启停，通知中心历史不依赖渠道是否打开。
- 状态栏只有一个含义：主页面最底部、文字极少的极扁小栏。必须实现，但全新配置默认关闭、不显示；用户显式开启才显示，选择持久化。用量和其他功能入口不得依赖状态栏出现。
- 通知/用量复用现有NotificationCenterView/UsageDetailsView及共享数据源；不增加嵌套的“辅助栏边栏”，不在每个浮动窗口重复全局入口。

## 生命周期和实现顺序

1. 在既有Dock布局增加浮动容器、窗口位置、页签顺序、选中页、原停靠位置。先用菜单提供“浮动此页/浮动整栏/停靠到左、右、底部”，之后完善拖拽。
2. 页面宿主与业务服务分离；同一控件先从原父级解除再挂载，普通页复用VM。关闭页面/浮动展示窗口默认隐藏展示，不隐式结束终端进程或辅助对话。
3. 终端先验证输出/滚动/焦点/IME保活。浏览器单独处理：现有BrowserViewHost脱离视觉树会释放原生WebView2控制器，不能只移动Control就宣称无损。必须验证窗口句柄变化、导航/历史/profile/登录态，以及无法保留的页面瞬态并如实说明。
4. 通知页完成三渠道语义迁移；窗口/页签不可见时第三渠道如何提醒需明确，不自动把用户正在看的浏览器切成通知页。保守默认：页签未读标记；可见通知页更新提示内容；短时浮层和系统通知由各自渠道负责。
5. 迁移原floating-window.json设置：保留系统/应用内提醒选择，把旧浮窗渠道映射新通知页渠道；旧窗口位置仅在有效时作为初始浮动通知容器位置。缺失状态栏偏好取false；既有显式用户选择保留。改前保留原数据，迁移版本化且重放幂等。
6. 新机制验证后才撤旧入口及重复实现。主窗口退出统一处理；重启遇显示器移除/缩放变化，把窗口恢复在可见工作区。停靠、显示隐藏和窗口置顶是不同命令。
