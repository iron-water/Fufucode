# AI 会话执行与交接协议

2026-10-14受管桌面任务回传：按 [交付回传协议](delivery-callback-protocol.md)，用户直接授权受管执行者向固定“主agent（管理）”主动发送交付/阻塞/协调，现有heartbeat每两小时补漏。M新派完整prompt附直接人类授权原文与来源，不靠父线程请求自行推定权限；在途任务不打断，工具缺失走补扫。最终回复仍展示卡，主控核实轮次结束和停写后审核；未实跑回传不写验收通过。下文人工转发仍适用于未纳管会话。

日期：2026-10-10。适用对象：主 agent M 与各 Codex/OMP 执行会话。与 [执行契约](execution-contract.md)、[任务提示词](launch-prompts.md) 共同作为 AI 开工、协调、交付与收编的执行依据。面向人类的会话图仅解释操作，不是 AI 协议真源。本协议没有实现自动监听、派单或合并软件，也不代表已创建执行会话。

## 1. 已有的开发结构与提示词

2026-10-10无人值守补充：用户已授权M自动管理其新建工作树内的执行agent。受管任务按[无人值守开发](unattended-development.md)执行；只有agent结束后提交交付卡入队，允许多个待审交付积压，M独立复核后整合或打回。下文人工转发方式仍适用于用户自行创建、未纳入管理的会话，不要求接管既有会话。

受管新运行使用[结构化事件v1](agent-event-protocol.md)：任务记录仍有人类交付卡，最终回复仅JSON delivery.card；M以review.decision审核，不能从回复中的“已整合/待修复”关键词猜判断。既有运行结束后再转换，不中途重启或读半成品。

`docs/tasks/launch-prompts.md` 包含任务目标、依赖、允许路径、验收、费用纪律和交付要求；`docs/tasks/execution-contract.md` 规定共同架构、文件所有权与验收门。执行者必须读实际源码，不凭文档目录名虚构接口。

用户先按会话图准备 Codex Worktree 或 OMP /worktree，再发送下面完整开工指令。只替换任务ID，不需要拼接多个提示词。任务ID示例：D1、O1、O3。

```text
本执行会话只负责【任务ID】及本任务的修复。按 docs/tasks/session-handoff-protocol.md 开工，不自动接其他任务。
先核对实际cwd和Git仓库，读取AGENTS.md、docs/AI_DEVELOPMENT_PLAN.md、docs/tasks/execution-contract.md、docs/tasks/session-handoff-protocol.md，以及docs/tasks/launch-prompts.md中本任务完整段落和引用任务书。
历史任务prompt内的C:\Projects\Fufucode只是搬迁前的主区位置：在本会话当前已准备好的独立worktree执行，不能切回主目录或旧路径。
输出开工身份卡：任务ID、软件/启动方式、实际目录、git worktree list、分支或detached HEAD、起点SHA、已有改动、允许范围、依赖证据。继承的用户改动不覆盖、不夹带提交。
依赖满足且工作树独立时直接实现，内部步骤自主连续推进。模型测试与试跑显式使用最低成本可用模型。按任务书验证，不把进程退出或回复结束当作完成。
遇到范围冲突/未交付公共接口时输出协调卡，继续可独立工作；不自行扩大范围、不要求用户随意开新线程。需要主会话处理的准确请求按手册给出。
任务收尾时主动生成完整交付卡，写入本任务记录并在最终回复直接展示，不等待用户提醒、不让用户填写。区分模块交付、待公共接线、整项验收；不自行整合main、不push、不清理工作树、不开始下一节点。
```

如果执行会话的工作树太旧、不包含本手册，由主会话核对其未提交/未合并内容后同步文档与所需基线，再启动；不能以未知状态直接拉取、重置或重建。用户无需手工运行集成命令。

## 2. 中途是否需要开新会话

正常情况不需要。同一任务的内部步骤、失败修复和上下文整理留在原会话。模型建议“这段可另开会话”不等于用户必须立即开。

只有发现原任务确实需要拆成独立并行任务、已有任务无法承接的新范围，或原会话不可恢复时，才提出新会话。执行者输出协调卡，由M判断复用现有负责人、亲自接线、调整范围或新增任务包。

新会话必须先有：任务ID、目标、软件、独立工作树、起点、允许文件、依赖、验收和完整开工提示词。未准备齐不让用户先开空白会话。接替原会话时先确保原写入者停止并核对代码，不能出现两个同任务写入者。

协调卡：

```text
类型：依赖 / 文件范围冲突 / 新范围 / 会话接替
本任务与工作树：
触发事实与证据：
缺少什么：接口、提交或明确文件所有权
已完成和仍可继续的独立部分：
建议处理：交现有负责人 / M接线 / 扩展范围 / 新任务
需要M作出的具体决定：
不能继续的部分与原因：
```

用户将协调卡发给M：

```text
这是【任务ID】的协调卡。请核对真实依赖与当前并行任务，优先复用现有负责人或由你接线，不默认让我开新会话。
请给出可直接转发的处理指令。如果确实要新增会话，先提供软件、Worktree选择、起点、任务范围和完整prompt。
处理局部阻塞，其他独立任务继续；不要未经授权创建对话或发送消息。
```

## 3. 什么时候需要主会话处理后才能开工

| 情况 | 执行会话怎样做 | M怎样做 |
| --- | --- | --- |
| 已解锁任务，独立工作树/文件范围明确 | 直接开工，不再逐项请求批准 | 维护进度即可 |
| 依赖G1/G2或指定任务未整合 | 只做不依赖接口的部分，报告阻塞 | 核实并整合依赖，明确解锁SHA/契约 |
| 准备修改另一任务负责的共享文件 | 不越界，先交协调卡 | 排队、调整所有权或主区接线 |
| OMP模块已写好但共享入口未接 | 交模块和接线说明，不能报整项完成 | 接线并执行必要整项验收 |
| 外部登录/付费/必须用户决定产品方向 | 记录阻塞，继续其他可做部分 | 明确需要用户什么，不假称验收通过 |

G1/G2依赖是“前置成果已整合且门通过”，不是另一个会话说完成就可以接线。常规可逆实施选择由执行者自行决定，不把主会话变成每一步审批者。

## 4. 结束后如何交接，下一步谁给提示词

所有执行任务的代码/原型交付都由M收编。设计选择可由用户直接在执行会话作出；交接不要求用户承担代码审查。模块待接线是有效的阶段交付，但对应产品任务仍未整项验收。

执行者必须在任务收尾时主动输出以下交付卡；不得只说“已完成，是否需要交付卡”。将卡写入本任务已有的 docs/records/任务ID-*.md 记录，在最终回复中直接展示便于转发；正文含提交SHA时先提交实现/记录，再补录实际SHA，不虚构尚未产生的提交。该收尾要求同时适用于修复后的重新交付。

阶段模块交付或因外部阻塞不能继续时也主动提供卡，如实标部分交付/阻塞/未完成，没有提交写“未提交”及原因。过程中出现需要M协调的事件时主动生成协调卡，不等用户发现。无卡的最终交付不符合协议；这些规则不把每次普通进度回复变成收尾。

```text
交付卡
任务ID与软件：
工作树绝对路径、分支/HEAD、起点SHA：
本任务提交SHA（多个提交注明范围）：
改动文件、继承用户改动的保护情况：
实际验证命令、结果、证据位置：
未运行验证与原因：
公共接线需求、接口/入口/依赖：
状态：模块交付待接线 / 提交待验收 / 外部阻塞 / 未完成
原会话是否仍在写代码：否（或明确说明）
```

用户将卡发给M，并发送：

```text
请接收这份交付，核对实际提交和范围，复核必要验证，完成允许的公共接线并整合到main；保护用户改动，不push、不改写历史。
不要仅按交付者口头结论标通过。失败给我可转发到原会话的修复prompt；成功更新进度/决策与解锁状态。
处理后必须给“下一步操作卡”：哪些原会话继续、哪些等待、是否需要新会话、每个新会话用Codex还是OMP、如何开启worktree、最新起点SHA，以及完整可直接发送的任务prompt。
在依赖/文件占用/并发空位满足时推荐下一项；无可开任务则说明等待什么。不要未经我明确要求创建新对话。
```

M每次协调或收编后给出的操作卡必须包含：

| 项目 | 输出要求 |
| --- | --- |
| 本次处理结果 | 已整合/待修复/待接线/外部阻塞，附事实 |
| 已整合基线 | main提交SHA，及必要接口记录 |
| 原会话 | 继续修复 / 等待 / 已验收，给准确指令 |
| 新会话 | 不需要，或任务ID+软件+worktree+完整prompt |
| 难度与模型建议 | 新任务综合评估L1-L4并给具体模型建议；打回标原始→当前等级和差值，保留原主模型，仅升级至少两级时提示可用更强子代理辅助。完整prompt首行含等级；测试仍最低成本 |
| 并行范围 | 与活跃任务的文件冲突、空位核对；未知则标未知 |
| 未解锁任务 | 等待哪项交付、验收或外部条件 |

“马上指导下一步”意味着M处理完成后主动输出操作卡，不意味着未验收就自动开下一项。原会话完成但没把信息交到M时，M不会自动知道。没有消息/监听授权，本流程依靠用户转发；授权指定Codex对话协调可减少转发，但终端OMP不是Codex侧边栏对话。

## 5. 进度状态，避免结论混淆

状态：待启动 → 执行中 → 模块交付待接线 / 提交待验收 → 已整合待验证 → 已验收。另有阻塞和待修复，不用“进程退出”作状态。

M在docs/progress.md记录任务ID、状态、工作树/来源、整合SHA、依赖、阻塞与下一步；执行者维护本任务docs/records记录，不并行改权威进度。已验收才解锁要求该任务完整可用的下游。未提交/未合并内容未核对前不回收工作树。

文档已定义流程，不代表实际跨会话通信、OMP迁移、集成或产品验收已经实跑。
# U 产品多任务线程补充（2026-10-10）

新自动开发产品以线程为节点，线程内多个任务可分别交付；部分打回须明确threadId/taskId/partId/runId/HEAD、被退回范围、原会话/模型/工作树与未受影响任务。原已接受决定与已集成部分保留，修复重新交付产生新版本；不可把整个线程回滚或清空。适配与验收见[U任务契约](automation-workbench.md)。下文当前CLI一任务一会话的开工方法保留给既有运行，不据此限制产品基数或迁移未知会话。
